## 1. 为什么"怎么点都不对"（按嫌疑度排序的根因）

### 🔴 P0 · OCR 的 native 层是空桩，所有"识别"恒返回空 —— 这是决定性根因

`client/app/src/main/cpp/CMakeLists.txt` 在找不到 ncnn/OpenCV 时会编译 `OcrStub.cpp` 空桩：

```cmake
find_package(ncnn QUIET)      # 仓库内没有任何 ncnn 预编译包 → 必然失败
find_package(OpenCV QUIET)
if (ncnn_FOUND AND OpenCV_FOUND) ... else() → SecurityBridge.cpp + OcrStub.cpp
```

而空桩原来的行为是**假成功**：`OcrStub.cpp` 的 `init` 无条件 `return JNI_TRUE`，
`detect` 返回一个"完全合法但内容为空"的 `OcrResult`（`strRes=""`、`textBlocks=[]`）。

后果链条（每一环都真实发生）：

| 环节 | 结果 |
|---|---|
| `OcrManager.detect()` | 返回非 null，但文本恒为空 |
| `StzbUiMatcher.classifyGameState()` | **恒返回 `UNKNOWN`** |
| `StzbUiMatcher.findButtons()` | **恒返回空表** |
| `EngineBridge.clickButton()` | **恒返回 false** |
| `EngineBridge.waitForState()` | **必然超时** |
| 四个战术 Flow 的【出征】/【确定】 | **永远点不到，只剩盲点** |

也就是说：**"点击根本不发生"，而不是"点偏了几像素"**。日志里看不出任何异常，
因为 `OcrManager` 还打印了「RapidOCR 引擎初始化成功，模型已加载进内存」。

### 🔴 P1 · 目标坐标本身是错的：屏幕中心 + 世界坐标断链 + 镜头不会移动

- 用户没点选地块时，兜底目标是**屏幕正中**：`OverlayWindowManager.kt`（`virtualWidth/2+80, 360`）、
  定时任务（`virtualWidth/2, virtualHeight/2`）、`DualTrackSafetyGate`（同上）。
- `DualTrackSafetyGate.kt` 会把军令里解析出的**世界坐标 `(782,451)` 直接丢弃**，
  注释自称"确保大地图沙盘世界坐标与屏幕虚拟像素严格解耦……屏幕操作点固定使用标准屏幕中心安全区"。
  于是"识别到了意图，却点在屏幕中间"。
- `EngineBridge.swipe()` 与 `AutoTouchService.swipeVirtual()` **全项目零调用** →
  **镜头永不移动**，多地块铺路在物理上不可能成立。
- `StzbUiMatcher.extractGameWorldCenterCoord()` 无人调用；
  `GameState.COORDINATE_SEARCH_DIALOG` 没有任何"输入坐标并跳转"的实现。

### 🟠 P2 · 视觉坐标系的 X 轴缩放不自洽（系统性偏差 12~24px）

旧实现：`virtualWidth` 向上对齐 16 字节，但 X/Y 缩放都写成 `physicalHeight/720`。两者不互逆：

| 分辨率 | 右边缘 X 误差 |
|---|---|
| 2340×1080 | +12 px |
| 3120×1440 | +16 px |
| 2772×1284 | **+24.3 px** |

误差随 X **线性增长**（左边准、右边不准），且**不是 ±1px 高斯抖动所能掩盖**的。

### 🟠 P3 · 选队标签与 ROI 是一式四份的硬编码常量

`RoadPavingFlow / ImmunityBreakFlow / SiegeSyncFlow / RaidDefenseFlow` 里各有一份
`startX=220f, stepX=140f, y=160f`；另有 `Rect(180,220,650,550)`、右下角 `360×160` 等。
非 16:9 或面板布局不同的机型上，会选不到部队 → 确定键点不亮 → 表现为"点击无效"。

### 🟡 P4 · inset 与旋转补偿是死代码，转屏后永久失配

`updateSafeInsets()` **零调用**（`insetLeft/Top` 恒为 0）；`virtualHeight` 是 `val` 永不可变；
`refreshMetrics()` 只在启动与建捕获时各调一次；全仓库**没有任何**旋转/尺寸变化监听。
一旦转屏，坐标映射与真实显示空间永久错位且无自愈路径。

### 🟡 P5 · 点击后没有可信的校验，且存在"假成功"

- 所有"点击是否生效"的确认都依赖 OCR → 在 P0 下**必然全部超时**，实际行为是"盲点 + 固定延时"。
- `SiegeSyncFlow`、`ImmunityBreakFlow` 忽略 `clickButton` 的返回值，仍然输出
  「🚀 击发成功！误差: xxx ms」——把"没点中"包装成"卡秒精准"。
- Shizuku 分支一旦有权限就**独占**点击链路，失败时**不回退**无障碍，而 `isTouchReady` 仍报"就绪"。

### 2.3 「军令识别」吃的是硬编码样本

### 3.2 你提的第 2 项：弹窗宽度 / 军师 / 无人托管

**弹窗宽度减少 1/3。** 关键发现：宽度**根本不是** XML 里写的 `320dp`——
`inflate(layout, null)` 不会生成根 LayoutParams，窗口用的是 `WRAP_CONTENT`，
真实宽度被 7 个 Tab 撑到约屏宽 79%；而定位于 `x = (屏宽 - 356) / 2` 却假设面板只有 356px 宽，
**于是面板整体右偏、右侧被推出屏幕**（最右的「日志」Tab 与「停止全部」被裁掉）。

修复：改为确定性宽度 `屏宽 × 0.53`（0.793 × 2/3 ≈ 0.53，即收窄三分之一），
定位改用 `CENTER_HORIZONTAL` 精确居中，彻底删掉那个 356 常量。
另外把胶囊位置/吸附边距从裸像素改成 dp（原先在非 3.0 密度机型上位置会漂移），
并修正取点标记把"屏幕绝对坐标当容器内边距"的错位。

**军师「识别军令 / 战报会诊」改为真实读屏。** 删除硬编码样本；OCR 读不到文字时
**明确报告"未能从画面读到文字 + OCR 状态 + 该切到哪个界面"**，而不是伪造一个"已解析虎牢关"。
同时删掉从未测量过的「18ms / <85MB」，如实说明这是规则引擎、无神经网络推理。

**「智能巡查」改造为真正的无人托管（新增 `AutoPilot.kt`）。** 它的语义是：
持续感知战场 → 自动收起干扰弹窗/迷路时回大地图 → 大地图空闲时按
「巡检守护 → 铺路 → 攻城」优先级自主下发（一次只跑一个，不与在跑任务抢控制权）→
目标集合变化才重新下发，避免反复触发。

它有一条**刻意的准入门槛**：屏幕捕获、触控通道、**OCR 引擎**三者任一不可用时，
**拒绝启动并给出具体原因**（显示在军师面板）。理由很直接：托管的核心是"自己判断该不该动手"，
感知不可用时开启托管只会得到一个"永远认不出界面、不断乱点"的机器。
一旦按 §5 的方式构建出真正带 OCR 的包，这个循环无需任何修改即可完整运转。

### 3.4 你提的第 4 项：坐标

**我的判断是：「把坐标与游戏内自带坐标（地图格坐标如 (228,132)）统一」是对的长期方向，
但它不是当前点不准的原因。** 真正的坐标类问题有三个，我修掉了两个：

### 3.6 第二轮补充：世界坐标统一 / 可标定锚点 / 点击校验 / OCR 构建通道

目标项 (4) 要求的「与游戏内自带坐标一致」在本轮落地为一个真实可用的世界坐标层。

**① 又挖出一个根因：坐标正则的格式根本不对。**
原 `PATTERN_COORDINATE` 期待 `X: 521, Y: 890`，而游戏 HUD 实际是
**城池名 + 括号坐标**，例如 `武威 (228,132)`（取自你提供的真机截图）。
也就是说这条识别**从来没成功过**，世界坐标整条链路自然全是断的。
现已新增 `PATTERN_HUD_COORD` 解析该格式，并保留旧格式兼容。

**② 新增世界坐标层 `MapCoordinateSystem.kt`**（`MapProjection` + `MapNavigator`）：
- `Calibration(tilePxX, tilePxY, centerWorldX, centerWorldY)`：每格像素数 + 镜头中心世界坐标，本地持久化；
- `worldToScreen` / `screenToWorld` / `dragDeltaToCenter`：双向换算与拖动位移反算；
- `calibrateFromTwoPoints(...)`：同一镜头下两点即可解出全部标定值；
- `readCurrentCenterWorld()` / `syncCenterFromHud()`：从 HUD 读数校正镜头中心，形成闭环；
- `selfTest()`：用合成标定值验证换算可逆 **以及拖动方向正确**（手指位移必须与目标方向相反），
  不依赖真机、不依赖 OCR；
- `MapNavigator.centerOn(...)`：真正拖动地图把目标对准镜头中心，且**信息不足时拒绝执行**
  （未标定就拒绝，而不是猜一个位移盲拖）。

**③ 新增可标定 UI 锚点表 `UiAnchors.kt`，替换 4 份硬编码。**
出征选队标签的 `startX=220f, stepX=140f, y=160f` 原先在 4 个 Flow 里各写一份，
而且那组常量是按 **1280 宽画布**量的——在 20:9 机型（设计画布宽 1600）上，
同一个 `x=220` 会落到面板里**不同的相对位置**。这正是"某些机型选不到部队 →
确定键点不亮"的成因。现在改为**按比例表达 + 可持久化标定**
（`Key` 点锚点 / `RectKey` 矩形锚点），4 个 Flow 统一走
`UiAnchors.troopTab(slot)` 与 `UiAnchors.rect(...)`；
`WatchdogRecovery` 的"空白区点击"也改由 `Key.MAP_BLANK` 提供，
真机位置不准时可单独标定，不必改代码发版。

**④ 世界坐标真正接进了铺路流程（不是摆设）。**
`PavingConfig` 新增 `worldTargetList`：提供时，流程会在点每一块地之前先用
`MapNavigator.centerOn(世界坐标)` 把镜头对准它，然后点**镜头中心**——
"点哪里"变成即时算出，而不是沿用取点时那个一次性屏幕点。
未标定时自动回退到屏幕坐标（保持原行为）。

**⑤ 补上点击效果校验 `EngineBridge.tapAndVerify()`。**
`tap()` 只保证手势派发成功，**不代表点中了**。新增按帧 8×8 均值哈希比对
点击前后画面、带偏移重试的校验；`WatchdogRecovery.dismissAnyDialog` 已改用它，
不再"只要 tap 返回 true 就当弹窗已关闭"。类注释里如实写明了它的局限：
**画面没变化不等于没点中**（有些操作本就不改变画面），不要当万能判据。

**⑥ 修掉一批"假成功"日志。**
铺路原先无论是否确认都打印「✅ 成功攻占第 N 块领地」，现在区分
「确认到免战罩」与「超时未确认（不计入成功数）」；
选队时 `detail.stamina ?: 100` 这种"没识别到就当成满体力满士气"的写法，
改为如实记录"未验证"。检测区域也从全屏收窄到目标点附近（原先任何金色 UI 都会误报占领）。

**⑦ 校验器升级为可复现的证据链。**
`tools/verify_refs.py` 现在除了资源引用一致性，还会对
`TacticalState.TaskType/Status`、`StzbUiMatcher.GameState/ButtonType`、
`UiAnchors.Key/RectKey`、`ImmunityMode` 等枚举常量，以及 9 个关键对象的成员引用
做 usage ↔ declaration 对账（本次共核对 16 组），能挡住"引用了不存在的成员"这类编译错误。
同时新增 workflow YAML 合法性校验。

**⑧ 新增独立的 OCR 构建通道 `build_apk_with_ocr.yml`（手动触发）。**
主流程 `build_apk.yml` 不提供 ncnn/OpenCV，因此编出的 APK 里 OCR 必然是空桩。
新工作流专门尝试 provision ncnn + OpenCV，并用 `-PncnnDir` / `-PopencvDir`
编译真实引擎，**失败也不会影响主流程出包**，并在 step summary 里明确打印
"真实引擎是否参与编译"。⚠️ 该工作流**未经实机验证**，首次运行很可能需要按失败日志调整下载地址与路径。

### 本轮靠推理抓到、但静态校验抓不到的坑

- **属性初始化顺序**：`autoPilotListener` 一度被声明在 `OverlayWindowManager` 的 `init{}` **之后**，
  而 Kotlin 按文本顺序初始化属性——`init` 里注册它时会拿到尚未初始化的 null。已上移修正。
- **嵌套类可见性**：`enum class` 嵌在 `object` 内是静态嵌套类，直接读外部 object 的私有表有
  可见性/限定名风险；已改为通过公开访问器 `isPointCalibrated` / `isRectCalibrated` 读取，彻底避开。
- **差点制造链接错误**：我原本打算把 `ocr_lite/src/main.cpp` 从 CMake 的 GLOB 里排除，
  查证后发现它承载的正是 `OcrEngine` 的三个 JNI 入口（不是命令行 main），排除会直接链接失败。

### 3.7 第三轮补充：标定向导 / 世界坐标贯通全流程 / 收尾假成功

**① 新增「标定」页签（第 8 个 Tab）——让世界坐标与 UI 锚点真正能被用户对上。**
上一轮 `MapProjection` / `UiAnchors` 虽已实现并可持久化，但**没有任何界面入口**，只能由代码侧调用；
那样"标定"就仍然是摆设。现在悬浮控制台多了一个「标定」页签：

| 按钮 | 作用 |
|---|---|
| ① 读取 HUD 坐标并记为基地 | 用 OCR 读右上角坐标读数，写入镜头中心 + 基地坐标（供镜头迷航归位） |
| ② 点选一块地并输入它的坐标 | **单点标定**：已知镜头中心世界坐标 + 点选点 + 该点世界坐标，直接解出每格像素数 |
| ③ 两点标定 | HUD 读不到时的兜底：两块地各自的坐标即可解出全部标定值 |
| ④ 标定地图空白点 | 让"收起浮层"的落点可标定（原先固定在纵向 62%，误触了只能改代码发版） |
| 清除全部标定 | 回到默认值 |

状态栏如实显示：地图投影是否已标定、UI 锚点已标定几项，以及
**OCR 不可用时明确告知「① 会失败、② 无法用，请用 ③」**——而不是让用户点一个注定失败的按钮。

一个细节：单点标定的数学是
`tilePx = (点选点 − 视口中心) / (该点世界坐标 − 镜头中心世界坐标)`，
因此点选的地块必须**离屏幕中心足够远**，否则分母趋零解不出来。
代码显式挡住了这种输入并说明原因，而不是算出一个荒谬的每格像素数。

**② 世界坐标贯通到全部流程，不再只有铺路。**
新增 `SiegeConfig.cityWorldCoord`、`ImmunityConfig.targetWorldCoord`，
攻城与卡免也改为"先对准镜头、再点镜头中心"。
定时任务持久化 `targetWorldX/Y`，触发铺路/攻城时一并把世界坐标交给流程；
编辑对话框与任务列表都会显示"世界坐标 (x,y)"或"⚠️未标定世界坐标"，
未标定时明确提示"镜头一旦移动该目标即失效"。

**③ 收尾假成功日志。**
- `SiegeSyncFlow`：原先拿到了 `clickButton(CONFIRM)` 的返回值却不用，无论成败都打印
  「🚀 击发成功！误差 xx ms」。现在成功才报成功，失败明确报
  「未能点击（原定误差 xx ms），本次击发未生效，请人工复核该队是否已出发」。
- `ImmunityBreakFlow`：原先 `fired` 变量取了却不用，无论成败都报「出征触发完毕，误差仅 xx ms」；
  现在失败会输出 FAILED 状态、写明确警告并返回 false。

**④ 结果：全项目的硬编码选队坐标与 ROI 已清零。**
核查结果：`140f / 220f / 160f / Rect(180,…)` 在 4 个 Flow 中**已无任何残留**，
仅存在于 `UiAnchors.kt`（单一来源，且注明是按 1280×720 折算的默认值）。

### 3.8 第四轮补充：真机实测几何 + 不依赖 OCR 的大地图判据

**① 不再用折算值，改用真机截图实测。**
把用户提供的真机截图（2712×1220）拿来做像素测量，而不是继续按 1280×720 折算：

- **HUD 坐标读数区**：原来的默认值 `(0.88, 0.09, 1.00, 0.22)` 是凭肉眼估的，
  实测会把上方「于禁冬至画像 / 分享赢888虎符」那条亮色横幅（实测 y 0.089–0.143）
  一起圈进来，给 OCR 引入无关文字。收紧为实测值 `(0.892, 0.126, 0.974, 0.214)`
  —— 坐标文字实测位于 x 0.9049–0.9598、y 0.1451–0.1943，裁剪已验证**只含** `武威 (228,132)`。
- **底部功能栏**：用白色标签字形做列簇分割，测出 5 段标签中心
  `0.0979 / 0.1433 / 0.1893 / 0.2353 / 0.2812`，**间距高度等距（0.0458）**、标签宽度一致（104px）。
  这种规整性本身就是测量正确的佐证。

**② 新增 `SceneFingerprint`：不依赖 OCR 的「是否在大地图」判据。**
这是本轮的核心。动机非常具体：OCR 失效时 `classifyGameState()` 恒为 `UNKNOWN`，
于是 `WatchdogRecovery.recoverToMainMap()` **即使本来就在大地图上也会反复盲点地图空白区**
——这正是用户能直接感知到的"乱点"。

原理：底部功能栏那 5 张卡片是**固定游戏美术**（位置固定、内容固定，是 HUD 而非世界内容），
对它们做 8×8 均值哈希即可判断"大地图 UI 是否在屏上"。指纹**自校准**
（用户站在大地图时点一次「⑤ 记录场景指纹」），因此不依赖我这边猜的模板，
不同分辨率/赛季皮肤各自校准，而且校准是用户可验证的动作。

**③ 阈值不是拍的，是用你的截图实测出来的。**
把 Kotlin 算法等价实现在 Python 里、对你的真实截图跑验证
（已固化为可重跑工具 `tools/validate_scene_fingerprint.py`）：

| 场景 | 实测汉明距离 |
|---|---|
| 同一张大地图截图自比 | 0 |
| **真实变体**：悬浮面板打开时的同一界面 | **1~2** |
| JPEG q=75 再压缩（模拟编码噪声） | 0 |
| 完全不同画面（App 竖屏界面） | **19~32** |

真实变化只造成 1~2 位差异，错误画面在 19 位以上。据此把阈值从 8 调到 **10**：
比真实变化留 5 倍余量，又远低于错误画面下限。

**为什么偏向宽容**：两种误判代价不对称——
*漏判*（明明是大地图却说不像）会让 `recoverToMainMap()` 退回盲点，正是要消除的行为；
*误判*（不像却说是）只是让后续 `waitForState` 失败重试一轮。因此阈值朝宽容一侧取。

工具还**纠正了我自己写错的一处预期**：我最初把"悬浮面板打开时的截图"归为"不应命中的反例"，
但它底部功能栏仍可见，命中 5/5 其实是**正确行为**。现已把工具的分类语义改成
`--variant`（同 UI，期望命中）与 `--other`（不同 UI，期望不命中），并在文档里写明这个边界。

**④ 这一判据能修掉什么、不能修掉什么（诚实边界）。**
- 能：`recoverToMainMap()` 在大地图上会立刻返回 true，不再盲点；`AutoPilot` 不再瞎"自愈"。
- 不能：它**只可能返回 MAIN_MAP**，无法区分地块菜单/出征面板等弹窗，
  因此其它场景识别仍然依赖 OCR。指纹未校准时返回 `null`（表示"没有结论"），
  调用方不得当作"不匹配"。
- 游戏大版本更新若改了底部功能栏美术，需要重新校准。

### 3.9 第五轮补充：标定入口补全 + CI OCR 通道加固

**① 标定入口补全到「部队标签」与「识别区域」。**
上一轮「标定」页签只覆盖地图投影、"地图空白点"、场景指纹；而 5 个部队标签锚点
（`TROOP_TAB_1..5`）和 3 个识别区域（部队卡片 / 行军耗时 / HUD 坐标区）仍然只有
**折算默认值**——那正是"某些机型选不到部队"的根源。现在补成两个引导式流程：

| 入口 | 流程 |
|---|---|
| ⑥ 标定出征部队标签 | 逐个槽位提示「请点选【部队N】标签的位置」→ 点一下即记录一格，自动进到下一格；只有 3 支队伍时按「取消」收工，已记录的保留 |
| ⑦ 标定识别区域 | 每个区域先后点**左上角**与**右下角**，自动归一化成矩形并持久化；两个区域依次引导 |

「取消」被复用为"结束引导式标定"的出口——这点很重要：玩家队伍数不固定，
若没有中途收工的出口，标定到第 4 格就会卡住。

**② 修掉一个会让 OCR 构建**直接失败**的坑。**
我最初打算把 OpenCV 的 `.so` 复制进 `jniLibs` 来保证运行时能加载。但
`build.gradle` 已经依赖 `com.quickbirdstudios:opencv:4.5.3.0`，该 AAR **自带**
`libopencv_java4.so`；再放一份同名库，APK 打包阶段就会因
`More than one file was found with OS independent path 'lib/arm64-v8a/libopencv_java4.so'` 直接失败。

正确做法是**不重复打包**：`libRapidOcr.so` 运行时动态加载 `libopencv_java4.so`，
由 AAR 提供即可。现在只对 ncnn 的 `.so` 做"有就打包"（它的 android 包多为静态库），
OpenCV 那份只做**校验**。

**③ CI 的 OCR 通道加固了三处。**
- **候选资产名依次尝试**：ncnn 的 android 包有 `-android` / `-android-vulkan` /
  `-android-shared` / `-android-vulkan-shared` 四种变体，现在逐个试，降低首次运行失败概率；
- **构建后校验 APK 内容**：直接 `unzip -l` 检查 `libRapidOcr.so` 与
  `libopencv_java4.so` 是否真的在包里，缺任何一个就**显式失败**——
  否则会出现"编译过了、装上一跑就 UnsatisfiedLinkError"这种最难查的情况；
- 产出摘要里打印 APK 大小与 native 库清单。

**④ 新增 CI shell 结构校验器 + 自测。**
本机没有可用的 bash（Git 自带的 bash 在沙箱下无法启动），`bash -n` 跑不了。
于是写了 `tools/check_ci_shell.py`：解析 workflow 的每个 `run:` 块，
检查 `if/fi`、`for/while/done`、`case/esac` 配对与双引号配平，
并正确屏蔽**引号内与注释里**的关键字。当前 14 个 run 块全部通过。

它同样配了自测 `tools/selftest_check_ci_shell.py`（15 个正反例）。
第一次自测就抓出两个**我自己的 bug**：
1. 只剥离了单引号，导致 `echo "if fi done"` 里的 `done` 被误算成循环结束；
2. 我的测试脚本写在了 PowerShell here-string 里，`$x` 被 PowerShell 插值污染。
两个都已修正。**一个"永远报 OK"的校验器和没有校验器一样危险**，所以每个校验器都要配反例。

### 3.10 第六轮补充：没有任何付费墙（商业化硬伤）+ 清完剩余死数据

**① 发现并处理了最严重的商业化问题：整套卡密体系是纯装饰。**
三处叠加，导致**应用完全没有付费墙**：

| 环节 | 事实 |
|---|---|
| Kotlin 调用 | `LicenseManager.checkLocalLicense()` / `activateOnline()` 在工程内**零调用**（唯一引用是 `KnowledgeBaseManager` 借它的 URL 做知识库热更） |
| 凭证签发 | `checkLocalLicense()` 在首次安装时**自己签发**一张永久旗舰凭证（原第 65–76 行） |
| 原生验签 | `SecurityBridge.cpp` 对签发用的魔法签名 `COMMERCIAL_MASTER_PERPETUAL` **无条件放行** |
| 云端端点 | `supabaseEndpointUrl` 仍是 `your-supabase-project` 占位符 → 离线分支必然命中 → **任意卡密都通过** |

后端 SQL、Edge Function、`tools/gen_cards.py` 全都在，但没有一个环节真正把关；
任何安装者自动获得"商业旗舰永久版"。

**处理方式（刻意不改默认行为，避免把你自己锁在门外）**：
- 新增 `LicenseGate`：把"无鉴权"变成一个**显式、可见、可一键关闭**的开关。
  `DEVELOPMENT_MODE_OPEN_ACCESS` 默认 `true` → 行为与修复前完全一致；
  但**日志会打出醒目警告**，**主界面状态栏会显示"授权：开发模式（无鉴权）"**，
  杜绝"不小心把没有付费墙的包发出去"。
- 真实门禁已经接好：悬浮窗里 5 个"会真的去点游戏"的入口
  （铺路 / 卡免 / 攻城 / 巡检 / 无人托管）都经过 `ensureLicense()`。
  把开关改成 `false` 后它们就会真正拦截并提示激活。
- `SecurityBridge.cpp` 增加 `ALLOW_MASTER_TOKEN` 宏（默认 1 保持现状，改 0 即关闭主控签名）。
- `LicenseManager` 里三处自签发路径全部改为**明确标注"开发模式签发（非真实授权）"**并打警告日志，
  不再谎称"商业旗舰永久版"。
- 类注释里写了商业发布的 5 步清单（关开关 → 部署 Supabase → 生成卡密 → 换真实端点 → 确认原生宏）。

**② 清完全部剩余死数据。**

| 字段 | 之前 | 现在 |

| `screenVirtualWidth/Height` | 零引用，且构成**第二套坐标基准** | **已删除**（唯一权威是 `CoordinateTransformer`） |

### 3.11 第七轮补充：激活界面 + 修正上一轮一个错误结论

**① 补上了激活界面（主界面新增「授权与激活」卡片）。**
上一轮把"无鉴权"做成了开关，但工程里**没有让用户输入卡密的入口**——
一旦把开关改成 `false`，用户将无处激活。现在补上：

- 状态行：按授权状态显示不同颜色（开发模式=黄、已授权=绿、未激活/熔断=红）；
- 「输入卡密激活」：弹窗输入 → `LicenseManager.activateOnline()` → 结果如实回显；
- 「重置授权」：清除本地凭证缓存（带确认说明）。

**② 修正上一轮的一个错误结论：只改那个开关其实**不生效**。**
上一轮我说"把 `DEVELOPMENT_MODE_OPEN_ACCESS` 改成 false 就真正拦截"。**这是错的。**
因为 `checkLocalLicense()` 仍会自己给自己签发一张**看起来完全合法**的永久凭证
（签名段固定为 `COMMERCIAL_MASTER_PERPETUAL`），门禁会把它当成已授权——
付费墙照样是摆设。

正确的做法是让门禁能区分「自签发开发凭证」与「服务端真实签名」。
已在 `LicenseGate` 中实现判据：凭证的签名段若等于那个固定串，即判为开发凭证、视为未授权。
判别式为什么可靠（已实测校对）：

| | 字符数 |
|---|---|
| 真实签名（32 字节 SHA-256 的 base64url） | **43** |
| 开发签名 `COMMERCIAL_MASTER_PERPETUAL` | **27** |

长度就不可能相同，因此不存在"真实凭证被误判为开发凭证"的情况。

**③ 顺带修掉一个真实健壮性问题。**
凭证是 `|` 分隔的固定 **6 段**格式（原生层 `parts.size() != 6` 即判非法），
而激活码直接来自用户输入。若其中含 `|`（实测会变成 7 段），凭证将永远无法通过校验。
现在在入口处就把它剔除，而不是指望用户不会输入。

**④ 给这段逻辑配了可运行的验证：`tools/selftest_license_token.py`（13 项全通过）。**
覆盖：三种自签发路径都能被识别；真实签名不被误判；长度论证；
空值/缺前缀/段数不足等边界；激活码含 `|` 的段数影响。
它同时**纠正了我注释里的一个笔误**——我把 27 字符写成了 26，脚本输出给出了真实值。

### 3.12 第八轮补充：找到并修掉一个会让 OCR 构建必然失败的缺陷

**① 一个具体缺陷：`${OpenCV_INCLUDE_DIRS}` 缺失。**
之前几轮我一直在说"提供 ncnn + OpenCV 就能编出可用的 OCR"。**这句话当时是错的。**

ocr_lite 的几乎所有头文件都 `#include <opencv2/core.hpp>` / `<opencv2/imgproc.hpp>`，
而 CMakeLists 的真实分支里：

```cmake
include_directories(
    ocr_lite/include
    ${CMAKE_CURRENT_SOURCE_DIR}
)                      # ← 没有 OpenCV 的头文件目录
target_link_libraries(RapidOcr ... ${OpenCV_LIBS})   # 库路径列表，不传递 include
```

`find_package(OpenCV)` 会设置 `OpenCV_INCLUDE_DIRS`，但链接用的是 `${OpenCV_LIBS}`——
那是**库文件路径的列表**，不是 imported target，**不会**传递 `INTERFACE_INCLUDE_DIRECTORIES`。
所以即使把 ncnn 与 OpenCV 都 provision 好了，构建仍然会以
`'opencv2/core.hpp' file not found` 失败。

已修正，并加了一条**配置期守卫**，把原本难以定位的编译错误变成清晰的配置错误：

```cmake
if (NOT OpenCV_INCLUDE_DIRS)
    message(FATAL_ERROR "找到了 OpenCV，但没有拿到 OpenCV_INCLUDE_DIRS，无法编译 ocr_lite…")
endif()
```

**② 为 native 构建写了静态校验器（本机可跑，不需要 NDK）。**
`tools/check_native_ocr_build.py` 核对这些**静态就能查证**的前置条件：

- 真实分支 `add_library(RapidOcr …)` **实际引用了哪些源文件**（会展开 `file(GLOB …)`），
  是否真的包含 ocr_lite（JNI 入口在 `ocr_lite/src/main.cpp`）与 `SecurityBridge.cpp`，
  且是否误含 `OcrStub.cpp`；
- `include_directories(...)` 参数里是否有 `${OpenCV_INCLUDE_DIRS}`；
- `target_link_libraries(RapidOcr ...)` 参数里是否有 `ncnn` / `jnigraphics`；
- **JNI 符号与签名**：把 `OcrEngine.kt` 的每个 `external fun` 与两个分支的 C++ 入口逐一比对
  （符号名、参数个数、参数类型、返回类型）；`SecurityBridge.kt` 同样核对；
- 两个分支不得同时定义同名 JNI 符号；
- 工程内 `#include "..."` 是否都能在已配置的 include 目录中解析到。

当前结果：**全部通过**（真实分支编译 10 个源文件、85 条 include 全部可解析）。

**③ 更值得说的是：这个校验器的第一版几乎是空转的，是反例自测把它揪出来的。**
我按惯例配了反例自测 `tools/selftest_native_ocr_check.py`：把 CMakeLists 复制到临时目录、
**故意注入已知缺陷**，再断言校验器能报出来。第一版结果：

| 注入的缺陷 | 第一版是否捕获 |
|---|---|
| 去掉 `${OpenCV_INCLUDE_DIRS}` | ❌ 漏 |
| 真实分支混入 `OcrStub.cpp` | ✅ 捕获 |
| 真实分支不链接 `ncnn` | ❌ 漏 |
| 真实分支不链接 `jnigraphics` | ❌ 漏 |
| 真实分支删掉 `main.cpp`（JNI 入口） | ❌ 漏 |

**5 个缺陷漏掉 4 个**。根因是我用"整个分支里是否出现某个字符串"来判断，而：

- `if (NOT OpenCV_INCLUDE_DIRS)` 这条**守卫语句**本身含有该字符串，于是把
  `include_directories` 里那一行删掉也照样"命中"；
- 注释里提到的文件名会被子串匹配当成真实的源文件列表（"真实分支包含 OcrStub.cpp"
  这个误报就是这么来的）；
- 源文件列表我是从**文件系统**推导的，而不是从 CMake 实际引用的，所以删掉 `file(GLOB …)`
  完全不影响结论。

已重写为**解析真实的函数调用参数**（`add_library` / `target_link_libraries` /
`include_directories`），并展开 `file(GLOB …)`。重写后自测 **6/6 全部符合预期**。

这件事的教训很直接：**校验器本身必须接受反例检验**。一个"永远说 OK"的校验器，
比没有校验器更危险——它会让人以为问题已经查过了。

### 3.13 第九轮补充：一个会直接掐死「无人托管」的状态机缺陷

**① 缺陷：任务状态下线后永不复位。**
`TacticalPipeline` 的四个 `startXxx()` 原先各自写成：

```kotlin
stopCurrentTask()
activeTaskType = <TYPE>
currentJob = scope.launch { ...flow... }
```

**任务正常结束时没有任何回调去清 `activeTaskType`**，于是 `currentTaskType`
会永久停留在一个非 null 值上。后果非常具体：

> 无人托管用 `currentTaskType != null` 判断"是否有任务在跑"。
> 第一个任务跑完之后，它会**永远认为还有任务在跑**，
> 此后再也不下发第二个任务，只是一直打印"大地图（有任务在跑）｜保持观察"。

也就是说：**「无人托管」只能干一件事，然后就永久呆住了。**
这正是"用着用着就不动了"那一类最难自查的问题——日志看起来一切正常。

**修法**：所有启动路径收敛到统一的 `launchTask(type, block)`，
用 `Job.invokeOnCompletion` 在任务结束（正常/异常/被取消）时复位状态并广播；
并且**用 Job 身份做校验**（`currentJob === job`），避免旧任务的完成回调
把新任务的状态误清掉。异常路径也会兜底记录并广播 `FAILED`
（原先协程里抛异常会在 `Dispatchers.Default` 上静默丢掉）。

**② 加了一道静态不变量，防止这个坑被重新引入。**
`tools/verify_refs.py` 新增「领域不变量」检查：规定 `activeTaskType` / `currentJob`
的**赋值只能出现在** `launchTask` / `stopCurrentTask` / `stopAll` 里——
在别处赋值就意味着绕过了完成回调。规则本身也配了反例自测
（`--selftest`）：规范写法 0 项、越权写法精确报出 2 项。

> 顺带记一笔：这个检查第一次跑就报"找不到目标文件"——又是**路径少了包名前缀**
> `com/stzb/assistant`。这个错我在 `check_members` 里已经犯过一次，属重复踩坑。
> 已修正，并把查找路径打进错误信息里，下次一眼能看出是路径问题而不是文件丢了。

**③ CI 的 OCR 通道：把"猜资产名"改成"查事实"。**
ncnn / OpenCV 的发布资产名会随版本变化。之前我用的是硬编码候选名 + 依次尝试，
本质是在猜。现在改为**先用 GitHub Releases API 列出该版本的全部资产名**，
再按正则挑选，并且**把全部资产名打印出来**，失败时可直接人工核对：

```bash
jq -r '.assets[].name' ncnn_release.json | sed 's/^/  - /'
URL=$(jq -r --arg p "$PAT" '.assets[] | select(.name|test($p)) | .browser_download_url' …)
```

选包优先级：静态包 → vulkan 包 → 任意 android 包（静态包不需要额外 `.so`）。

### 3.14 第十轮补充：无人托管自身的状态机同样会「静默失效」

上一轮修的是 `TacticalPipeline` 的任务状态；这一轮把同样的眼光转向 `AutoPilot` 自己。
它在 `loop()` 里用了三个局部变量当一次性标志：`raidStarted` / `pavingSignature` / `siegeDone`。
其中**两个置位后永不复位**，各自对应一个真实故障：

| 标志 | 不复位的后果 |
|---|---|
| `raidStarted` | 巡检守护一旦异常退出、或被「停止当前」手动停掉，**夜间防护就静默消失了**——托管再也不会把它拉起来。这是安全类功能最不该出现的行为：用户以为有守护，其实没有。 |
| `siegeDone` | 用户改了攻城目标、或改了命中时刻，托管也不会重新武装——因为它只记得"我已经派过一次攻城了"。 |

顺带还有一个不好排查的点：**没有防抖动**。如果某个流程刚下发就失败，
`currentTaskType` 会立刻回到 null，托管下一拍（4~6 秒后）又会下发一次，
如果没有冷却，就会形成热循环。

**修法**（三层）：

1. **状态改为自愈式成员状态**，集中在 `dispatchWhenIdle` / `ensureRaidPatrol` /
   `resetRuntimeState` 里维护，并在每次 `start()` 时重置；
2. **巡检守护可重新拉起**：当"已拉起、但当前任务已经不是巡检"且距上次拉起超过
   60 秒冷却时重新拉起，并**把原因明确写进日志**
   （"巡检守护已不在运行（被手动停止或异常退出），托管将在冷却期后重新拉起；
   若不想被拉起，请关闭无人托管。"）——而不是悄悄重启让人莫名其妙；
3. **铺路与攻城改用"签名"而非布尔量**：目标集合/世界坐标/命中时刻任一变化即视为
   新目标、自动重新下发。`siegeDone` 这个布尔量因此被彻底去掉。

另外 `describeIdle()` 现在会区分"目标已武装但还没到下发时刻"这类状态并如实说明，
而不是笼统地说"已配置的目标均已下发"。

**防回归**：给 `AutoPilot` 也加了同类的**领域不变量**规则
（那四个状态只允许在上面三个函数里赋值），并把 `--selftest` **泛化为自动覆盖所有规则**——
对每条规则自动合成"合规写法／越权写法"两个最小用例，今后新增规则不需要手写测试。
当前 2 条规则、4 个用例全部符合预期。

> 过程小记：改这一轮时遇到一次 `ReplaceFileW EIO (Win32 1175)`（文件替换失败的瞬时占用）。
> 我没有假设编辑成功，而是先 `grep` 确认了"第一处改动已落盘、第二处未落盘"，再重试。

### 3.15 第十一轮补充：把七套校验器收成"一键回归"，并接进 CI

**① 新增 `tools/run_all_checks.py`。**
之前这些校验器是散落的脚本，得逐个手敲——既容易漏，也不构成"可交付的验证入口"。
现在一条命令跑完全部 8 项，并给出逐项 PASS/FAIL 与耗时：

```
PASS | refs                   | 资源/成员/findViewById/领域不变量 一致性
PASS | refs-selftest          | 领域不变量规则的反例自测
PASS | native-ocr             | native OCR 构建前置条件
PASS | native-ocr-selftest    | native 校验器的反例自测（注入缺陷）
PASS | ci-shell               | CI shell 结构
PASS | ci-shell-selftest      | CI shell 校验器的反例自测
PASS | license-token          | 授权凭证判别逻辑自测
PASS | scene-fingerprint      | 场景指纹算法实测（需要真机截图）
通过 8 / 失败 0 / 跳过 0
```

两个设计决定值得一提：
* **不启子进程**，全部用 `importlib` 在当前进程内调用各校验器的 `main()`
  ——绕开管道相关的平台限制，也便于统一捕获输出；
* **截图类检查优雅跳过**：真机截图不适合进仓库，所以缺图时**跳过并说明原因**，
  而不是让 CI 变红；需要时可用 `--fingerprint-map` 或环境变量提供，`--strict` 则让"跳过也算失败"。

**② 新增 `.github/workflows/verify.yml`。**
这个工作流**不需要 JDK / Android SDK / NDK**，几十秒就能跑完，
因此在每次 push 与 PR 上都会跑一遍，并把结果写进 step summary。
它给项目补上了一个真正的验证入口——你 push 之后能直接看到这七套检查的结果，
不必依赖我在本地手敲命令。CI shell 结构校验的覆盖面也随之从 14 个 run 块升到 **17 个**。

**③ 又一次踩到同一类问题：文档承诺 ≠ 实现。**
我给 `run_all_checks.py` 写了 `--strict`（"缺截图也算失败"），
但第一版代码里跳过分支**根本没读 `required` 字段**——`--strict` 完全无效。
是自测时对比两种模式才发现：非严格模式报"跳过 1"，加上 `--strict` 仍然是
"跳过 1、退出码 0"，与文档不符。已修正，现在 `--strict` 会如实报 FAIL 并返回 1。

这个坑在本次会话里已经是**第三次**同一类型：

| # | 位置 | "承诺" 与 "实现" 的落差 |
|---|---|---|
| 1 | `CoordinateTransformer.updateSafeInsets` | 注释宣称"挖孔屏/刘海自动补偿"，实际**零调用**，inset 恒为 0 |
| 2 | `ModelAssetManager.getFullDiagnosticReport` | 资产缺失时把降级路径写成"XX 通道就绪"，等于**把失败说成成功** |
| 3 | 我自己的 `--strict` | 文档写了严格模式，代码里没实现 |

三处的共同点：**行为没有被任何检查覆盖，于是偏离长期无人发现。**
这也是为什么这个会话最后把力气花在"给每一处承诺配一条可运行的检查"上——
包括给校验器自己配反例自测。

### 3.16 第十二轮补充：让「点不到按键」变成可诊断的三态原因

**① 问题：失败原因被一个 `Boolean` 抹掉了。**
`EngineBridge.clickButton()` 原先只返回 `true/false`，而四个战术流程里有 **13 处**调用。
失败时调用方只知道"没点到"，写出来的日志也就只能是笼统的
「敌方跳板地出征按键未点亮或不可点击」——**分不清到底卡在哪一环**：

| 真实情况 | 该做什么 | 原先能否区分 |
|---|---|---|
| OCR 引擎根本没编译进来 / 初始化失败 | 需要带 ncnn 的构建，改代码没用 | ❌ |
| 引擎可用，但这一帧一个字都没读到（过渡动画/黑屏/识别区域需标定） | 等界面稳定或标定区域 | ❌ |
| 读到了文字，但没匹配上目标按键（不在该界面，或游戏改了文案） | 检查场景判定与关键词 | ❌ |

这三种在真机排查时的处置方式**完全不同**，却长得一模一样。

**② 修法：三态诊断，且**不额外付一次 OCR 的代价**。**
`StzbUiMatcher` 新增：

```kotlin
enum class ButtonLookupFailure(val desc: String) {
    OCR_UNAVAILABLE("OCR 引擎不可用（构建期缺 ncnn/OpenCV 或初始化失败），无法识别任何文字"),
    NO_TEXT("画面中未识别到任何文字（可能处于过渡动画/黑屏，或识别区域需要标定）"),
    NO_MATCH("识别到文字但未匹配上目标按键（可能当前不在该界面，或游戏改动了按键文案）")
}
data class ButtonLookup(val button: ButtonResult?, val failure: ButtonLookupFailure?, val scannedTextCount: Int)
fun findButtonWithReason(bitmap: Bitmap, type: ButtonType): ButtonLookup
```

关键实现细节：把原来的 `findButtons()` 拆成「跑一次 OCR」+「在文本块里匹配」两步，
诊断版本复用**同一批文本块**。否则为了拿到失败原因就得再识别一遍——
OCR 是全流程里最贵的一步，这种"为了方便诊断而让每次点击慢一倍"的写法是不能接受的。
`scannedTextCount` 也一并带出来，日志里能看出"这一帧到底读到了多少字"。

`EngineBridge` 相应地改成 `clickButtonDiagnosed(type): ClickOutcome`，
并把原因写进**用户可见的游戏内日志**（不需要 adb 就能看到）：

```
未能点击【出征】：识别到文字但未匹配上目标按键（可能当前不在该界面，或游戏改动了按键文案）（读到 37 个文本块）
```

**③ 顺手删掉了那个会丢失诊断信息的布尔重载。**
13 处调用点全部改用诊断版本后，`clickButton(): Boolean` 变成**零调用**。
按本项目一贯的标准（死代码要删，而不是"留着说不定有用"），我把这个重载**删除**了，
并在原位留了一段说明。删除的好处是：**编译器会强制未来的调用点走诊断路径**，
少一个能让失败原因消失的入口。这比再加一条 grep 检查更可靠。

**④ 顺带修掉一个真实的小缺陷。**
`RoadPavingFlow` 里点【确定出征】失败后会"二次寻找"，但**第二次的结果被丢弃了**——
即使第二次也失败，日志也不会再多说一句。现在两次的结果都会如实报告。

**⑤ 证据**：一键回归 8/8 通过；三态原因均已定义；`grep` 确认全工程已无未经诊断的
`EngineBridge.clickButton(` 调用点。

### 3.17 第十三轮补充：把"识别最近灵不灵"变成当场可看

**① 问题：识别是否在退化，挂机时完全无从判断。**
上一轮把**单次**按键失败分成了三态原因，但单次失败说明不了问题——
一次过渡动画也会失败。真正要回答的是"**最近这段时间识别整体灵不灵**"，
而在这一轮之前，OCR 是否可用只在 App 启动时打一行日志，之后再无任何可观测信号。
真机上表现为：某个战术流程莫名失败，然后只能靠猜。

**② 新增 `RecognitionHealth`：极轻量的识别健康度统计。**
它只做一件小事——把每次场景判定与按键定位的结果累计起来：

```
识别健康度（场景样本 142，按键样本 37）
· 场景判定成功率: 94%（UNKNOWN 9 次）
· 按键定位成功率: 78%
· 平均文本块: 31.4 个/帧；整帧无文字 3/179 次识别
· 最近: 按键 CONFIRM 定位成功（读到 34 个文本块）
```

并在两种典型退化上给出明确提示，而不是让人自己算：

* OCR 引擎不可用 → "⚠️ 上述失败源于此，不是画面问题（需要带 ncnn/OpenCV 的构建）"
* 超过一半的识别读不到任何文字 → "⚠️ 请检查识别区域标定，或确认游戏界面是否已更新"

**③ 两个实现细节值得说明。**

* **只在两个地方挂钩，且用"包一层"的方式**：
  `classifyGameState()` 与 `findButtonWithReason()` 内部都有多个 `return`，
  逐个加统计必然漏。因此各自包一层——内部实现改名、外层统一记录——
  将来新增分支也不会漏统计。
* **统计口径**：`recordTextFrame` 同时被**场景判定**与**按键定位**调用。
  这一点很重要：场景判定是挂机时最频繁的识别调用（每 4~6 秒一次），
  只统计按键定位的话，"整帧无文字"的比例会因为样本太少而没有意义。
  措辞也相应写成"`3/179` **次识别**"，而不是含糊的"帧"。
* 另外把模板"分不开的两个概念"显式区分：成功率**无样本时是 `NaN`**（显示"—（无样本）"），
  不是 0、也不是 1——**绝不把"一次都没识别过"显示成"100% 成功"**。

**④ 展示位置**：悬浮窗「标定」页签的诊断区（`refreshCalibrateDisplay`）。
这里本来就是"排查识别问题"的去处，与地图投影、UI 锚点、场景指纹并列。
诚实说明其局限：这是**按需快照**——打开该页签或完成一次标定动作时刷新，
不是每秒自动重绘。

**⑤ 证据**：一键回归 8/8；`verify_refs.py` 新增 `RecognitionHealth` 成员对账，
报告"4 个成员引用全部已声明"（即 `recordScene` / `recordButton` / `recordTextFrame` /
`summary` 四个调用点都对应真实声明，调用名写错会被拦下）。

### 3.18 第十四轮补充：把"点了但界面没跳"与"根本没点到"分开

**① 问题：`clickButton + waitForState` 这个松散组合会把两件事混成一句日志。**
四个流程里原先普遍是这样写的：

```kotlin
val attack = EngineBridge.clickButtonDiagnosed(ButtonType.ATTACK)
if (!attack.clicked) { logWarn("未能点击【出征】：${attack.detail}") }
val dialogReady = EngineBridge.waitForState(GameState.TROOP_DISPATCH_DIALOG, 3000)
if (!dialogReady) { logWarn("出征面板未弹出，执行弹窗自愈...") }
```

点击成功、但界面没跳转时，日志只会说「出征面板未弹出」——
排查的人会往**场景判定**方向去找，而真实原因可能是**点击落点偏了**。
两者的排查方向完全不同。

**② 修法：`clickAndExpect(type, expected, timeoutMs, attempts)`。**
一次调用同时完成"点"与"确认落到了预期界面"，并明确区分：

```kotlin
data class ClickAndExpect(
    val clicked: Boolean,        // 是否至少成功派发过点击手势
    val sceneReached: Boolean,   // 期望场景是否真的出现
    val attemptsUsed: Int,
    val detail: String
) { val ok: Boolean get() = clicked && sceneReached }
```

日志因此能直接说清是哪一种：

```
未能进入出征选队面板：已点击 [ATTACK]，但 3000ms 内未出现 TROOP_DISPATCH_DIALOG（尝试 2 次…）
未能进入出征选队面板：未能定位按键 [ATTACK]：画面中未识别到任何文字（…）（读到 0 个文本块）
```

**③ 两个判据的分工，以及为什么重试不是无脑的。**
* **帧差**（[tapAndVerify]）适合"预期会引起变化的通用点击"，但**不适合地图**——
  地图本身持续有动画（行军、云影），帧差几乎恒为正，会大量假阳性。
* **场景判定**适合"预期会落到某个具体界面"的点击。
  两者各有适用面，因此这一轮是把**后者**补上，而不是拿它替换前者。

重试策略也是刻意的，不是为了显得稳健：
* `OCR_UNAVAILABLE` → **立即放弃**。引擎没编译进来，重试一百次结果一样，
  只会白白消耗挂机时间与操作痕迹；
* 其余失败（没读到文字 / 匹配不上 / 派发失败 / 界面没跳）→ 静置 250ms 后重试，
  因为过渡动画造成的失败确实可能自愈。250ms 这个值也是权衡过的：
  过渡动画通常几十到几百毫秒，但压秒类操作对时间敏感，不能给更长。

**④ 顺带修掉我上一轮引入的一个语义错误。**
上一轮我给 `clickButtonDiagnosed` 加"手势派发失败"时，错误地复用了 `NO_MATCH`
（它的含义是"识别到文字但没匹配上按键"）。这让排查方向被指错：
本该去查触控通道，却会让人去查关键词与场景。
现在拆出独立状态 `TAP_DISPATCH_FAILED("已定位到按键，但手势派发失败（触控通道可能被中断）")`。
**这是我自己上轮留下的缺陷，这一轮才发现。**

**⑤ 有意**不**改的地方。**
压秒类点击（`ImmunityBreakFlow` 与 `SiegeSyncFlow` 的【确定出征】、
`RaidDefenseFlow` 的两处确认）**保持"点完立即返回"**，不套用 `clickAndExpect`。
理由很明确：那几处是毫秒精度的压秒触发，点完之后再去等 3 秒的场景确认
本身就是错的。它们已经在此前几轮改成了如实报告失败原因。

**⑥ 证据**：一键回归 8/8 通过；调用点审计显示
`clickAndExpect` 7 处（4 个流程）+ 压秒类 `clickButtonDiagnosed` 4 处，
正是上面那条有意划出的边界。

### 3.19 第十五轮补充：定时任务的"静默缩水"与三个连带的陷阱

这一轮按计划审查定时任务的编排交互。功能本身是好的（能建、能改、能删、默认无内置任务、
无目标会跳过而不是乱点），但审出一个**静默的行为落差**和三个连带陷阱。

**① 主问题：点了 5 块地，定时任务只铺 1 块，界面一句话都不说。**
编辑器里只取第一块：

```kotlin
TacticalState.TaskType.ROAD_PAVING -> pickedPavingPoints.firstOrNull()
```

触发侧也确实只处理那一块（`targetTileList = listOf(target)`）。
于是用户的真实体验是："我在铺路页签选了 5 块地，建了个定时任务，结果只铺了 1 块，
另外 4 块呢？"——而界面上**从头到尾没有任何提示**，计划列表里也只显示 1 个目标坐标。

**修法**：任务改为携带完整目标集合。
* 新增 `TargetPoint(x, y, worldX, worldY)` 与 `ScheduledTask.allTargets()`；
* 新增可选字段 `extraTargetsRaw`（编码 `"x,y,wx,wy;x,y,wx,wy"`），
  **主字段 `targetX/targetY` 保持不变**，因此已经存在本地的旧数据照常工作；
* 编辑器的提示从"目标: (x, y)"改为"**将处理 N 块地**（你在「铺路」页签点选的全部目标）"，
  并按世界坐标的齐备情况给出三种明确说明；
* 计划列表里多目标会显示"共 N 块地"，保存时也会 Toast 确认"到点将处理 N 块地"。

**② 陷阱一：两个列表是按下标对应的，天真写法会造成"对准 A 却点 B"。**
`RoadPavingFlow` 里 `worldTargetList.getOrNull(index)` 与 `targetTileList[index]`
是**按下标配对**的。如果顺手写成"只把有世界坐标的那些收集起来"，
第 3 块地的世界坐标就会被套到第 2 块地上——**镜头对准 A，手指点在 B**。
这种错误在真机上表现为"偶尔铺错地"，极难归因。
现在的做法是全有或全无：要么全部用世界坐标，要么全部退回屏幕坐标，两者始终一一对应；
出现混合时（部分地块未标定）明确记录"本次只处理有世界坐标的 M 块"。

**③ 陷阱二：编码格式会被区域设置破坏。**
`"%.2f"` 在德语/法语等区域输出的是**逗号**小数点，而这个编码正好用逗号做字段分隔符。
后果是"任务能保存、重启后目标全丢"——一个只在特定语言环境下出现的丢数据 bug。
已强制 `Locale.US`，并把展示用的坐标格式化也一并统一。
（这个坑最早是从旧的 `"%.0f".format(...)` 展示代码里注意到的。）

**④ 新增静态检查：持久化字段必须"写入与读出成对"。**
加字段时我**差点**只写了 `loadTasks` 的读取、忘了 `saveTasks` 的 `put()`——
那同样会表现为"设置能保存、重启后悄悄丢"。既然这类错误有固定形状，就该静态拦住：
`verify_refs.py` 现在会解析 `ScheduledTask` 的主构造参数，逐一确认每个字段名
都同时出现在 `saveTasks`（写入）与 `loadTasks`（读取）里。

配套的反例自测有 3 个用例：成对 → 0 项；漏写 → 精确 1 项；漏读 → 精确 1 项。

**⑤ 顺带删掉一处死代码。**
`resolveWorldForType()` 只取第一个目标的世界坐标，多目标改造后已无调用方，按标准移除。
留着一个"看起来能用、实际会漏掉其余目标"的入口，比删掉更危险。

**⑥ 自测本身也出过一次错，值得记一笔。**
持久化自测第一版**直接复用了真实 spec**（`data_class = "ScheduledTask"`），
却喂给它声明 `Demo` 的合成代码，于是永远报「找不到 data class」。
定位方式是打印实际的解析结果（`fields: ['alpha','beta']` 正常、问题只在类名不匹配）。
**一个永远失败的用例，和一个永远说 OK 的校验器一样没有价值。**

**⑦ 证据**：一键回归 8/8；`verify_refs --selftest` 7 个用例全部符合预期
（4 个领域不变量 + 3 个持久化对账）；多目标链路
`编辑器 → encodeExtraTargets → addTask/updateTask → saveTasks → loadTasks → allTargets → 触发`
逐点核对符号全部就位。

### 3.20 第十六轮补充：知识库热更会把本地搞坏（含一个字典序比较 bug）

这一轮审的是热更链路。功能描述听起来完备（多游戏切换、离线内置兜底、云端热更、本地分级缓存），
但**采用云端配置这条路径上没有任何把关**，加上一个隐藏的比较错误，足以让用户失去全部战术能力。

**① 主 bug：版本号是字符串，却用 `>=` 比较——这是字典序，不是数值序。**
`profileVersion` 的类型是 `String`，而装载缓存时写的是：

```kotlin
if (cachedProfile.profileVersion >= baseProfile.profileVersion) {   // ← 字典序
```

Kotlin 对 String 的 `<` `>` `>=` `<=` 会走 `compareTo`，**编译完全通过**，但结论是错的：

| 表达式 | 字典序结果 | 真实语义 |
|---|---|---|
| `"9" >= "10"` | **true**（'9' > '1'） | 版本 9 比 10 旧 → 旧缓存会**压住**新内置版本 |
| `"1.10.0" < "1.9.0"` | **true** | 1.10.0 比 1.9.0 新 → 合法新缓存反被**拒绝** |

用户看到的是"明明提示热更成功了，重启后又变回旧版"，或者"怎么都热更不上去"。
已新增 `GameProfile.compareVersion()` 做**数值**分段比较，装载与更新两条路径都改用它。

**② 采用云端配置前没有任何校验——空壳配置会被接受并写盘。**
`GameProfile.fromJson` 对缺失字段一律用默认值兜底，所以一份**结构合法但内容为空**的 JSON
会被"成功"解析成：守军库为空、按键语义表为空、`targetPackage` 为空。原实现会
**先写盘、再切换内存**，于是：

* 用户**静默**失去全部战术能力（守军评估没人可评、按键别名全空）；
* 更糟的是这份空壳**已经持久化**，下次冷启动还会继续用它。

已新增 `GameProfile.validateFor(gameId)` 作为采用前的闸门：
game_id 必须匹配、版本号非空、守军库非空、按键语义表非空、targetPackage 非空。
不通过就**拒绝采用且不改动本地任何东西**，并把原因写进日志与返回消息。

**③ 更新路径压根没有版本比较，完全信任服务端的 `has_new_version` 标志。**
服务端配置错误（或缓存错乱）时会把旧版本发下来，客户端照单全收并写盘——等于**主动降级**。
现在要求版本必须**严格更新**，同版或旧版一律忽略并如实说明。

**④ 就地写入不是原子的。**
原先直接 `cacheFile.writeText(...)`。进程被杀或磁盘写满会留下半截 JSON：
下次启动解析失败降级到内置版本（不会崩，这点原来是对的），
但**这次"已生效"的更新会凭空消失**，用户只会觉得"更新了但没变化"。
现在先写 `.tmp` 再 `renameTo`，改名失败则明确报错且不改动本地配置。

**⑤ `resetToBuiltIn` 会把当前激活的游戏悄悄换掉。**
它无条件调用 `loadProfileForGame()`，而后者**总是**给 `activeProfile` 赋值。
于是"重置另一个游戏的知识库"会把当前激活档换过去，
而 `SharedPreferences` 里的 `active_game_id` 还是旧值——状态不一致，
下次冷启动又翻回来，表现为"切来切去搞不清在用哪套"。
现在只有重置的正是当前激活游戏时才重新装载。

**⑥ 两处次要但真实的问题。**
* 非 2xx 时直接 `return`，**响应体不会被消费也不会被关闭**，连接一直挂到超时；
  长时间挂机时会累积。已用 `try/finally` 显式关闭。
* `UpdateResult.currentVersion` 在**切换之后**才读 `activeProfile.profileVersion`；
  若检查的不是当前游戏，报出来的会是另一个游戏的版本号。
  已改为用 `currentVersionFor(context, gameId)` 取"该游戏当前生效版本"。

**⑦ 新增静态规则：版本号不得用 `<`/`>`/`<=`/`>=` 直接比较。**
这类错误编译照过、运行期悄悄出错，正是最该静态拦住的一类。
`verify_refs.py` 现在扫描全部 Kotlin 文件（当前 49 个），
凡名字带 `version` 的标识符参与大小比较即报错，要求改用 `compareVersion()`。

**⑧ 这道新规则的反例自测，立刻抓出了规则自己的漏报。**
4 个用例里"常量在左侧"那条失败了：第一版正则只允许**标识符**作操作数，
于是 `if ("1.0" < profileVersion)` 这种真实写法被漏掉。已放开为允许数字字面量。
**如果我没写这条自测，就会带着一个会漏报的规则继续往下走。**

> 过程小记：改这条正则时我曾把 Python 代码误替换成一行 `//` 注释（非法 Python），
> 发现的当下就改回了正确实现。这类"手一抖"的错误，正是本轮一直在讨论的同一类问题。

**⑨ 证据**：一键回归 8/8；`verify_refs --selftest` 共 **11 个用例**全部符合预期
（4 领域不变量 + 3 持久化对账 + 4 版本号比较）；版本号规则扫描 49 个 Kotlin 文件、0 问题
（即那个字典序比较已是全工程唯一一处，且已消除）。

### 3.21 第十七轮补充：屏幕捕获在转屏时会**失败**甚至**崩溃**，以及一条能自动抓"死状态"的新规则

**① 最严重的问题：转屏重建设计在 Android 14+ 上必然失败。**
`ScreenCaptureService` 原先的旋转处理是"销毁捕获面 → 用同一个 MediaProjection
重新 `createVirtualDisplay()`"。但 **Android 14(API 34) 起，一个 MediaProjection 实例
只能用于调用一次 `createVirtualDisplay()`**，再次调用抛 `IllegalStateException`。
也就是说这套自愈逻辑在 Android 14+ 上**一次都不会成功**，而是直接走失败分支。

而这套逻辑是坐标体系的地基：它一失败，转屏后坐标与显示空间就永久失配——
前面所有坐标工作全部作废。

**修法**：改用**官方支持的原地调整**方式 `VirtualDisplay.resize()` + `setSurface()`，
不重新调用 `createVirtualDisplay`（见 `tryResizeInPlace()`）；原路径只作为老设备兜底。
顺序上也做了处理：**先换上新 ImageReader 再关闭旧的**，反之会让解析线程拿到已关闭的实例。

**② 转屏期间会崩溃。**
`captureCurrentFrame()` 里 `imageReader?.acquireLatestImage()` 写在 **try 之外**：

```kotlin
val image: Image = imageReader?.acquireLatestImage() ?: return null   // ← try 外
return try { ... } catch (e: Exception) { ... }
```

而几何调整会在主线程**关闭并替换** `imageReader`。两者恰好相撞时，
`acquireLatestImage()` 抛出的 `IllegalStateException` 会**直接冒泡给调用方**，也就是崩溃。
现在：取本地快照、把 acquire 移进 try、字段加 `@Volatile`、异常按"可恢复的瞬时情况"降级为返回 null。

**③ 一次失败就永久停捕获。**
原实现重建失败即 `stopCapture()`。转屏瞬间的失败往往只是瞬时的，
用户看到的却是"转一下屏就再也识别不了了，还得重新授权屏幕捕获"。
现在先按 600ms 延时重试，连续 2 次失败才停，并明确写出"请重新授权屏幕捕获"。

**④ 冗余回调导致的无谓重建。**
`onDisplayChanged` 表示"逻辑显示的属性发生了变化"，**并不只**在几何变化时触发
（刷新率/显示模式变化也会触发），旋转过程中还会连发数次。
原实现每收到一次就无条件拆掉重建。现在记录"当前捕获面是按哪组几何建的"
（物理分辨率 + 旋转角 + 画布尺寸的指纹），只有几何真的变了才动。

**⑤ 一处静默失效：显示监听可能根本没注册上。**
原实现 `registerDisplayListener(listener, null)` 用的是**调用线程的 Looper**；
在没有 Looper 的线程上注册会抛异常，而那里被 `try/catch` 吞掉，
表现为"旋转处理静默失效"——日志里什么都看不出来。
现在显式使用主线程 Looper，并在失败时用 `Log.e` 明确说出后果。

**⑥ 顺带清掉三个模块里的"死状态"，并撤掉虚假声明。**
新增的静态规则（见 ⑦）在真实工程里报出 **7 处只写不读的字段，零误报**：

| 位置 | 字段 | 处理 |
|---|---|---|
| `EdgeSlmEngine` | `isModelWeightLoaded` / `isRagLoaded` / `modelPath` / `ragPath` | 删除，并改写类注释与探测日志 |
| `YoloDetector` | `modelFilePath` | 删除，并把"权重加载成功"改为如实说明 |
| `ScreenCaptureService` | `captureWidth` / `captureHeight` | 删除（`captureCurrentFrame` 已改为以帧自身尺寸为准） |

其中 `EdgeSlmEngine` 尤其典型：它的类注释声称"主通道加载端侧 INT4 GGUF/MNN 权重
进行多步条件因果生成，无权重时自动无缝切换"，但三个公开方法**全是正则**，
那套字段**从未被读取**。现在注释如实写明"这是正则语义提取器，没有权重参与推理"，
探测日志也从"通道已就绪"改成"发现权重文件，但工程内没有能推理它的实现，不影响任何行为"。
`YoloDetector` 同理。

**⑦ 新增静态规则：只写不读的私有字段。**
这一类"死状态"在本项目里反复出现，且每次都伪装成"功能已就绪"——
`isModelWeightLoaded`（赋值 5 次、读取 0 次）、`projectionResultCode/Data`
（看着像为重建会话做好了准备，实际从未被读取）。
它们不报错、编译器不管，只会让人误以为某件事已经在做。
`verify_refs.py` 现在会扫描全部 Kotlin 文件（当前 49 个），
把"全工程只有赋值、没有读取"的私有字段全部报出来。

配套反例自测 2 条：有读取 → 不报；只有赋值 → 精确报 1 项。

**⑧ 证据**：一键回归 8/8；`verify_refs --selftest` 共 **13 个用例**全部符合预期
（4 领域不变量 + 3 持久化对账 + 4 版本号比较 + 2 只写不读）；
只写不读规则从"报出 7 项"到"0 项"，逐项都已处理。

### 3.22 第十八轮补充：让"识别根本不存在"在主界面上一眼可见

**① 缺口：主界面从不显示 OCR 状态。**
核对需求时发现，`MainActivity` 里 **OCR 相关引用为零**。而默认构建里 native OCR 是**空桩**
（见 §2 与 §5 的 P0）——也就是说：**整套产品最核心的能力缺席，而主界面完全不提示。**
用户只能等某个战术流程莫名失败，再去猜是哪里不对。这与本项目一贯的"缺失不可见"是同一个病。

**② 修法：运行环境卡片下新增 OCR 状态行 + "查看识别环境详情"。**
三种状态必须分开，否则会把"还没初始化完"误报成"不可用"：

| 状态 | 界面文案 |
|---|---|
| 就绪 | `文字识别（OCR）：✅ 引擎就绪（native 推理可用）` |
| 失败 | `文字识别（OCR）：❌ 不可用` + 具体原因 + "请用带 ncnn/OpenCV 的方式构建后再试" |
| 尚未尝试 | `文字识别（OCR）：正在初始化…` |

细节：
* OCR 初始化在 `App` 里是**异步预热**的，所以除了立即刷新，还延迟 1.5s / 4s 各补刷一次，
  避免界面一直停在"正在初始化…"；`onDestroy` 里 `removeCallbacksAndMessages(null)`，
  防止 Activity 销毁后仍被延迟任务持有。
* "查看识别环境详情"把 `ModelAssetManager.describeAvailability()` 的**资产级盘点**一次摊开，
  使"到底缺哪一块"一目了然，而不必去翻 logcat。

**③ 新增静态规则：关键能力对象必须被界面层引用。**
把这次的教训固化下来——"决定整套能力是否成立"的对象，界面层必须引用它：

```
信息 : 关键能力界面可见性: 已核对 2 组标志
```

当前覆盖 `OcrManager`（决定场景判定/按键定位/坐标读取能否成立）与
`LicenseGate`（授权状态若不体现，用户无法判断自己为什么被拦截）。

**④ 写这条规则时我自己连踩三个坑，都值得记下来。**

| # | 坑 | 表现 | 修正 |
|---|---|---|---|
| 1 | 路径用 `startswith("ui/")` | `relpath` 得到的是 `com/stzb/assistant/ui/...`，不以 `ui/` 开头 → 把刚接好的线判成"没接" | 改为按路径中的目录段匹配 |
| 2 | 正则排除了前面的 `.` | 全限定名 `com.stzb.assistant.ocr.OcrManager` 前面正好是 `.` → 同样把刚接好的线判成"没接" | 改成"只要不是更长标识符的一部分" |
| 3 | 粒度做到**成员级** | 代码里常写 `val ocr = …OcrManager` 然后 `ocr.isEngineAvailable`，字面看不到 `OcrManager.isEngineAvailable` → 假阳性 | 粒度降到**对象级**（见下） |

第 3 条带来了一个明确的原则：

> **检查器不应该规定产品代码的写法。** 当检查器产生假阳性时，要修的是**检查器**，
> 而不是为了迁就它去改产品代码（那叫本末倒置）。
> 而"界面层根本不引用该对象"这一条，已经足以覆盖历史上的真实缺陷
> （`MainActivity` 里 OCR 引用为零），所以粒度取到对象名即可。

**⑤ 证据**：一键回归 8/8；`verify_refs --selftest` 共 **16 个用例**全部符合预期
（4 领域不变量 + 3 持久化对账 + 4 版本号比较 + 2 只写不读 + 3 界面可见性）。
其中界面可见性的 3 个用例**专门钉住上面第 2、3 两个坑**
（全限定名必须算引用、别名写法必须算引用、界面层没引用必须报出来）。

### 3.23 第十九轮补充：补上卡秒偏移入口，并修掉两个让"卡秒"失去意义的时序问题

**① 补上最后一个不可调的参数：攻城卡秒偏移。**
`hitOffsetSeconds` 此前**硬编码 60 秒且界面完全看不到**，用户无法表达"我要压到 21:00:00 整"。
现在攻城任务里多了一个数字输入框（其余类型自动隐藏），并在计划列表里显示"卡秒偏移 Ns"。

一个刻意的取舍：输入非法（非整数 / 超出 5~3600）时**明确报错并中止保存**，
而不是悄悄回落到 60 秒——悄悄回落会让用户以为自己设的 90 秒生效了，到点却按 60 秒打。

**② 找到一个让卡秒**失去意义**的抖动。**
命中时刻原先是这样算的：

```kotlin
targetBaseHitEpochMs = System.currentTimeMillis() + task.hitOffsetSeconds * 1000L
```

而调度器是**每 15 秒轮询一次**时钟，触发实际发生在那一分钟内的**不确定时刻**。
于是用户设"20:59 触发 + 偏移 60 秒"期望 21:00:00 触敌，
实际可能落在 **21:00:03 ~ 21:00:14**——最多 14 秒抖动。
对一个毫秒级的卡秒功能来说，这个抖动足以让整件事失去意义。

已改为按**计划时刻本身**计算基准（`scheduledEpochMsFor()` 把 `"HH:mm"` 解析成今天该时刻的绝对时间戳），
抖动因此只影响"提前量"的长短，不再污染命中时刻。同时把"实际触发晚了多少毫秒"打进日志，
让延迟变成可观测的事实而不是猜测。

**③ 命中时刻已过去时，拒绝下发而不是照常出征。**
卡秒的价值就在那一秒。若按计划基准算出的命中时刻已经过去，
原先会照常往下走（等于在错误的时机把部队送上去）。
现在**明确跳过并说明**，让用户去调偏移或把任务时间提前。

**④ 顺带发现并修掉 `SiegeSyncFlow` 里一个同源的静默失败。**
测算不出真实行军耗时时，流程会用兜底估算（主力 150 秒 / 拆迁 370 秒），
并算出 `optimalDispatchEpochMs = 命中时刻 − 行军耗时 − 补偿`。
**若行军耗时超过剩余时间，这个时刻就落在过去**，而流程会照常继续：
时刻表打印出"倒计时: -90s"，部队仍被派出——**卡秒静默失败**。

现在在测算之后、出征之前加了一道**可行性预检**：只要有任一队伍的"最晚出征时刻"已经过去，
就取消本次集火，并明确告诉用户还差多少、任务至少要提前多少秒：

```
⚠️ 卡秒不可行，本次集火已取消：主力(部队1) 应在 1699999999999 前出征，已晚 90s。
原因：行军耗时 + 提前量超过了距离命中时刻的剩余时间。
请把任务时间至少提前 180 秒，或增大卡秒偏移。
```

**⑤ 证据**：一键回归 8/8；确认全工程已无 `System.currentTimeMillis() + task.hitOffsetSeconds`
形式的旧算法（grep 为空）；卡秒链路
`界面输入 → 校验 → addTask/updateTask → 持久化 → 按计划基准算命中时刻 → 可行性预检 → 出征`
逐点已核对符号就位。

### 3.24 第二十轮补充：给按键定位补上"不依赖 OCR"的第二条路（含一次方向纠正）

**① 缘起：按键定位此前只有一条路。**
识别按键的唯一方式是 OCR 读文字 → 匹配关键词 → 取文字框中心。
默认构建里 native OCR 是空桩，于是**整条路失效**——"点不到按键""点击不准"都源于此。
而游戏的按键是**固定美术**，模板匹配不需要训练、不需要模型、不需要网络，
在 OCR 完全不可用时**照样能工作**。这两条路是互补的：
OCR 适应"改了文案"，模板适应"读不出字"。

**② 我先犯了一个错：重复造轮子。**
我新写了一个纯 Java 的 `TemplateMatcher`（灰度降采样 + ZNCC），
**然后**才发现工程里已经有一个 `OpenCvMatcher`——它用 `Imgproc.matchTemplate` +
`TM_CCOEFF_NORMED`（数学上就是归一化互相关），还带多尺度版本。
**我应该在动手前先搜一遍的。**

更关键的是：`OpenCvMatcher` **除了 `init` 之外没有任何调用方**，`assets/templates/` 也是空的。
它就是需求 (5) 说的那种"实现了却没人用"——一个**现成的、能力完好的摆设**。

本机沙箱不允许我删除子目录里的文件（`Remove-Modify` 均被拒绝），
因此处理方式是**把它降级为兜底**，而不是留着一份平行实现：
* 主通道 = `OpenCvMatcher`（原生实现，快，且已有实现）；
* 兜底 = 纯 Java `TemplateMatcher`（**仅在 `OpenCVLoader.initDebug()` 失败时**使用——
  该调用在某些 ABI/打包方式下确实会失败，那时至少还能定位）。
两条通道都带同一条**区分度判据**。
> 如果你希望只保留一份实现，`TemplateMatcher.kt` 可以直接删除——
> 它在当前代码里的唯一职责就是"没有 OpenCV 时别彻底没得用"。

**③ 离线实测：在真机截图上验证算法，并据此发现现有实现的一个真缺陷。**
新增 `tools/validate_template_matcher.py`：用 Python 逐步复刻同一套数学
（灰度块平均降采样 + ZNCC + 非重叠次高分），在真机截图上跑四类检验：

| 检验 | 结果 |
|---|---|
| ① 能命中同一位置 | 命中偏差 **1px**，分数 **1.0000**，区分度 0.5563 |
| ①b 分数应接近 1 | 1.0000 |
| ② 在**另一界面**里不应命中 | 最高分仅 **0.38**（< 0.85 阈值）→ 正确拒绝 |
| ③ **抗亮度变化**（×0.75 / +40） | 仍命中同一位置，分数仍 1.0000 —— 这就是选归一化互相关而非像素差的理由 |
| ④ **重复图案应拒绝** | 最高分 1.0、次高分 **1.0**、区分度 **0** → 正确拒绝 |

> **数字订正（见第四十轮）**：上表是当时那版夹具跑出来的。后来发现夹具把帧框与模板框
> 写死成绝对像素，只有 ≥1800x1160 的图装得下；1080 高的真机截图会被 PIL 用黑边补齐、
> 模板裁在空白上——于是报出来的 FAIL 是**夹具坏了**，不是算法坏了。
> 夹具按图片尺寸比例化之后，同一批检验在真机上的数字变成"偏差 **0px** / 跨界面负例 **≤0.67**"，
> 并且量出一个当时那套夹具**看不见**的算法缺陷（降采样块网格的相位损失），修复见第四十轮。
> 第 ④ 条的结论本身仍然成立：它指出的 `OpenCvMatcher` 缺区分度判据这一缺陷是真的。

第 ④ 条直接指出了 `OpenCvMatcher` 的缺陷：它原实现只判断 `maxVal >= threshold`，
**没有区分度判据**。于是画面里出现重复美术（多个相同图标、多个"确定"）时，
它会自信地报"找到了"，而调用方可能点到错的那个。
已补上 `peakDistinctiveness()`（把最佳邻域用 −1 填掉后取次高）与
`MIN_DISTINCTIVENESS = 0.04f`（取在"重复≈0"与"唯一≈0.55"之间）。
实测同时也**验证了它原有的 `threshold = 0.75f` 是合理的**（真命中 1.0，跨界面最高 0.38）。

**④ 接线：模板库 + 两条通道 + 随用随学。**
* `ButtonTemplateStore`：每个按键一个 PNG（放 `filesDir/button_templates/`），
  用文件而非 prefs——小图 base64 会撑爆 prefs，而 prefs 是全量重写的；
* `lookupButton` 现在有两条通道：OCR 优先，失败则走模板匹配；**两条都带区分度判据**；
* **随用随学**：OCR 成功定位某按键时，顺手把那一小片登记成模板。
  这样等哪天 OCR 不可用了，同一个按键仍然点得到；
* 给 `OpenCvMatcher` 补了 `loadTemplateFromBitmap()` / `isAvailable` /
  `invalidateTemplate()`——原实现只能从 `assets/` 载入，运行期登记的模板根本进不去，
  这正是它一直没人用得上的原因之一；
* 清掉了 `EngineBridge` 里那个"import 了 OpenCvMatcher 却从不使用"的误导性导入。

**⑤ 诚实说明当前**还差哪一步**。**
模板匹配要能用，必须先有模板。现在有两条来源：随用随学（需要 OCR 至少成功过一次）
与手动登记。**手动登记入口还没做**——因此在"OCR 是空桩"的当前构建里，
模板库不会有内容，这条通道暂时是**通了但没货**的状态。
下一轮我会补上「标定」页签里的手动登记入口（复用现有十字准星），
那一步做完，"没有 OCR 也能点准"才真正成立。

**⑥ 证据**：一键回归 8/8；模板算法在真机截图上 **6/6** 通过；
新补的区分度判据有实测数值支撑（重复图案区分度 0 会被拒，唯一目标 0.5563 会被采用）。

### 3.25 第二十一轮补充：补上手动登记入口，让"没有 OCR 也能点准"真正成立

上一轮把模板匹配的通道接好了，但**缺一个入口**：模板库没有任何来源，

或
```

**④ "清除全部标定"也一并清掉模板库**，避免出现"我以为清干净了，其实还留着旧模板"。

**⑤ 至此这条链路是完整的**（每一步都已核对符号就位）：

   → refreshCalibrateDisplay 显示 → lookupButton 用模板定位

**⑥ 过程中的一个自查**：我这一轮两次把"插入"错写成"替换"，分别误删了
`MapProjection.clearCalibration()` 一行与 `cropRectFor()` 的 `val l = ...` 一行。

### 3.26 第二十二轮补充：给模板匹配配上"当场可验证"，并收掉一个同源缺陷

**① 最重要的一件：把真机验证做成一次点击。**
模板匹配的命中率**只能在真机上确认**，而我没有设备。与其让人去翻 logcat，
不如把它变成可操作的检查——「标定」页签新增 **⑨ 试匹配已登记按键**：
选一个按键 → 抓当前帧 → 走一遍真实定位链路 → 把结论**直接摊在对话框里**：

```

这样"登记出来的模板到底有没有用"就不再需要猜。实现上有一处细节：

**不计入识别健康度统计**——一次手工试验不该污染挂机期间的观测。

**② 收掉上一轮留下的一个同源缺陷。**
上一轮只给 `OpenCvMatcher.match()` 加了区分度判据，`matchMultiScale()` **还缺**。

现在两层共用同一道判据，且只接受**同时通过分数与区分度**的那一层。

**③ 新增一条无假阳性的不变量：枚举可达性。**
本轮的教训是：我给标定流程加了 `PickTarget.BUTTON_TEMPLATE`，
而"新增枚举值却漏接某个入口"在本项目很容易发生——枚举值一旦没人启动它，

`startCrosshairPicker(PickTarget.X)` 调用（配 2 个反例自测：全有 → 0 项；缺一个 → 精确 1 项）。

**④ 我刻意**没有**做"每个 when 是否覆盖全部枚举常量"的检查。**
理由值得写下来：那种检查会误报。例如 `OverlayWindowManager` 里第一个
`when (target)` 只负责"应用选点结果"，未列出的常量落到空分支是**有意**的。
**一个会误报的检查比没有检查更糟**——它会训练人去忽略它。
所以只做能清除判断的那一类（可达性），而不是看起来很全面、实际制造噪音的那一类。

（4 领域不变量 + 3 持久化 + 4 版本号 + 2 只写不读 + 3 界面可见性 + 2 可达性）；

### 3.28 第二十四轮补充：**量出**一个 10 像素的固定偏移，并修掉它

这一轮不再加检查器，而是去做一件能真正验证"点击准不准"的事：
**把坐标变换的数学离线复刻一遍，然后跟真值比。** 结论是一个实打实的缺陷。

**① 缺陷：镜头中心被取整，引入与每格像素成正比的固定偏移。**
`MapProjection.calibrateFromTwoPoints()` 解出镜头中心后做了 `roundToInt()`：

```kotlin
centerWorldX = centerWx.roundToInt(),   // ← 镜头中心本来是连续量
```

而所有换算都在用 `(world - center) * tilePx`——**中心差半格，就是半个格子的偏差**。
离线量化结果（`tools/validate_coordinate_math.py`，与真值对比）：

| 每格像素 | 取整带来的最大位置误差 |
|---|---|
| 8px（地图缩小） | 3.20px |
| 14px | 5.60px |
| 25px（地图放大） | **10.00px** |
| 任意 | **不取整时 = 0.00px** |

地图缩小时每格仅 8px，3.2px 已接近**半个格子**——这正是"差一点点、点到隔壁"的形态。

**② 一个方法论上的教训值得记下来。**
我同时做了"屏幕 → 世界 → 屏幕"的往返测试，**结果是 0.00px**——
因为往返用的都是同一个（被取整的）标定，它是**自洽**的，误差只在**与真值比较**时才暴露。
**如果我只写往返测试，就会得出"坐标数学没问题"的错误结论。**

**③ 修法：镜头中心改为 `Float`，不再取整。**
* `Calibration.centerWorldX/Y`：`Int` → `Float`，并在 KDoc 里写清为什么必须保留小数（附上面那张表）；
* 去掉 `calibrateFromTwoPoints` 里的 `roundToInt()`；
* 持久化改为存/读 `Double`。**向后兼容**：旧版本存进去的是整数，
  而 `JSONObject.getDouble()` 对 `Integer` 同样有效，因此老用户的标定值不会失效；
* 对外报告"当前在哪一格"的地方（`Result.Reached.centerWorld`）仍然 `roundToInt()`——
  那是一个"格子"的语义，取整是对的；**标定内部保留小数**不受影响。

**④ 这个改动牵动 9 处，其中 7 处必须显式转换。**
Kotlin **不做隐式数值转换**（`Int` 不能直接赋给 `Float` 变量），因此
`hud.first`、`500`、`c.first`、`world.first`、`cal.getInt(...)` 这些位置
都必须写成 `.toFloat()` / `500f` / `getDouble(...).toFloat()`。
漏掉任意一处都是编译错误——而这类错误我的校验器**查不出来**，
所以我是逐处读回确认的（`grep centerWorldX =` 全部核对过）。

**⑤ 顺带验证了一件一直只是"假设"的事：画布推导是等比的。**
`virtualWidth = round(720 * W / H)` 之后，两轴缩放比必须几乎相等，
否则会有一条轴系统性偏移。在 10 种真实分辨率上测量：

* 本机真机 2712x1220：画布 1601x720，两轴相对差 **0.030%**，右边缘偏差 **0.81px**；
* 最差的是 2K 竖屏 1440x3120：相对差 0.093%，边缘偏差 **1.33px**；
* 其余 8 种基本为 0。

所以画布推导本身是健全的，**不需要再引入 16 字节对齐**（那反而会破坏等比）。

**⑥ 把这次测量变成了永久的回归检查。**
`tools/validate_coordinate_math.py` 现在带断言（而不是只打印数字），
并接进一键回归，成为第 9 项：

```
PASS | coord-math | 坐标变换数学验证（画布等比/标定还原/往返一致）
```

它的四条断言分别是：画布等比（边缘偏差 < 1.5px）；**当前实现位置误差为 0**；
**旧实现误差 > 1px**（证明这个修复确实有意义，而不是改了个无关紧要的地方）；
往返偏差不超过一格。

**⑦ 过程小记**：写这个 Python 脚本时我又在中文串里嵌了双引号
（`"含"取整代价"量化"`）导致语法错误——与前面几次同一个毛病，当场修掉了。

**⑧ 证据**：一键回归 **9/9** 通过；`verify_refs --selftest` 24 个用例通过；
坐标数学 4 项断言全部符合预期；`centerWorldX` 全部 9 处赋值已逐处核对为 Float 语义。

### 3.29 第二十五轮补充：压秒流程原来在"目标时刻之后才开始瞄准"

这一轮把同样的方法用到**压秒**（卡秒）上。和坐标一样，它是纯算术，可以离线证明；
而且**差一秒就白干**，值得单独量。

**① 缺陷：等到目标时刻，才去定位按键——定位耗时被整个算进误差。**
两个压秒流程原先都是这个形状：

```kotlin
while (isRunning.get()) {                    // 等
    if (System.currentTimeMillis() >= timingPlan.optimalDispatchEpochMs) break
    delay(5)
}
val fire = EngineBridge.clickButtonDiagnosed(ButtonType.CONFIRM)   // ← 到点了才开始"瞄准"
```

而 `clickButtonDiagnosed` 要**抓屏 + OCR/模板匹配 + 派发手势**。
也就是说：**手势实际落在「目标时刻 + 定位耗时」**，而这段耗时从未被补偿。

离线量化（`tools/validate_timing_math.py`）：

| 定位耗时（假设） | 旧实现迟到 | 新实现迟到 |
|---|---|---|
| 30ms | 40ms | 10ms |
| 80ms | 90ms | 10ms |
| 200ms | **210ms** | 10ms |
| 400ms | **410ms** | 10ms |

注意这里严格区分了两件事：
* **「旧实现迟到量 == 定位耗时」是恒等式**，与机型无关，可以证明；
* **定位耗时本身（30~400ms）是假设区间**——本机没有设备，我**没有**测量它。
  真机上的实际值决定旧实现到底晚打多少；而新实现**不依赖这个值**。

**② 修法：先架枪，后扣扳机。**
新增 `EngineBridge.prepareButtonTap()`（只定位、不点击）与 `firePreparedTap()`（只派发手势，
并返回**派发那一刻**的时间戳）：

* `ImmunityBreakFlow`：在倒计时开始**之前**定位【确定出征】；
* `SiegeSyncFlow`：在 `prepareTroopPanel` 之后、精确等待**之前**定位
  （面板是逐队打开的，所以定位点必须放在打开面板之后）。

时间戳也一并纠正：原先取在点击**返回之后**，会让误差看起来比实际小；
现在取在 `tap()` **之前**——"手势派发时刻"才是压秒要对齐的物理事件。

**③ 顺带把"余量"这件事写明白，并加了迟到告警。**
`SiegeSyncFlow` 原先写死"提前 4 秒开面板"，我把它提为 `PANEL_PREP_MARGIN_MS`
并注明**这个余量必须覆盖 `prepareTroopPanel` + `prepareButtonTap` 的全部耗时**——
余量不够的后果是**直接晚打**，而晚打在集火里可能比不打更糟。

两个流程都新增了 `LATE_TOLERANCE_MS = 150L`：派发时刻晚于容忍量时**必须显式告警**并说明可能原因，
而不是把"晚了 400ms"当成"卡秒成功"打印出去——这与前几轮修掉的"把失败包装成成功"是同一类问题。

**④ 新增第 10 项回归检查。** `tools/validate_timing_math.py` 带 6 条断言：
公式恒等式（触敌 − 出征点 == 行军耗时 + 补偿）；剩余时间不足时出征点必然落在过去；
旧实现迟到量与定位耗时是恒等关系；新实现迟到量与识别耗时**无关**；
最坏情形旧实现晚打 ≥200ms；空转分辨率 + 派发耗时的三倍仍低于容忍阈值（保证不会频繁误报）。

**⑤ 证据**：一键回归 **10/10** 通过；`grep` 确认两个压秒流程里
**已无**"等完再定位点击"的残留（`clickButtonDiagnosed(CONFIRM)` 在压秒路径中为零）。

### 3.30 第二十六轮补充：**"我没读到守军"曾被报告成"强烈推荐去打"**

这一轮量的是**决策逻辑**。选错队/评错级会白送兵，比"点不准"更伤，
而且这类错误是**静默的**——它会给出一个看起来合理的结论。

**① 最严重的发现：空输入被判为 SAFE，并输出鼓励进攻的推荐语。**
`DefenderEvaluator.evaluate` 原先从 `var maxRiskTier = SafetyTier.SAFE` 起算，
只在"更高"时更新。因此当**一个守军名字都没读到**时（OCR 不可用、或这一帧没读到名字），
循环不执行，直接返回 SAFE，推荐语是：

> 🟢 极佳软柿子守军，战损极低，**推荐主力立刻出征收割！**

**"什么都没读到"被包装成"强烈推荐去打"。** 这比其他假阴性更危险：
它不是不报，而是**主动推动用户去做一个可能团灭的决定**。

修法：新增 `SafetyTier.UNKNOWN`（权重 0），空输入时**提前返回**并明确说
"无法判断该地是否可打"；`maxRiskTier` 改为从 UNKNOWN 起算，只要读到任何一个守军就会被真实结果覆盖。

> 一个刻意的细节：`when (maxRiskTier)` 是**表达式**，新增枚举值会让编译器在那里报错，
> 迫使我去处理它。这类"响亮的失败"正是我想要的——
> 相比之下，如果 `when` 带个 `else`，同样的遗漏就会变成静默。

**② 顺手核实了一个"我以为可能有问题"的地方——结果假设不成立，就不改。**
我怀疑 `threat_score` 缺失时会被解析成 0，而 `tierForScore(0)` 会返回 SAFE——
那同样会让"字段缺失"变成"判定为白给"。
查下来是 `h.optInt("threat_score", 2)`，默认 **2（MODERATE）**，是保守的。
**所以这里没有缺陷，我没有动它。** 记录这一点是为了说明：不是每个怀疑都会变成改动。

**③ 另一个发现：整套守军评估当前**没有任何调用方**。**
`EngineBridge.evaluateDefenderPanel` 全工程**零调用**——
也就是说"打了这块地会不会白送兵"这个能力，代码是齐的，但**没人用它**，
属于需求 (5) 里那种"摆设"。我**没有**擅自把它接进铺路流程，因为那是一个产品决定：
它需要先打开「查看守军」面板（依赖 OCR），还要决定在哪里呈现结论。
这一条列为待你决定的事（见 §4）。

**④ 新增第 11 项回归检查：**`tools/validate_decision_logic.py`。
它不抽查例子，而是**枚举整个输入空间**并断言必须成立的**性质**：

| 性质 | 内容 | 覆盖 |
|---|---|---|
| P1 | 空/纯空白输入必须判为 UNKNOWN，且推荐语**不得含**鼓励进攻措辞 | 4 种空输入形态 × 词表 |
| P2 | 读到守军即不再停留在 UNKNOWN；未知武将取 MODERATE（**不得是 SAFE**） | 全部列表 |
| P3 | 单调性：评分越高，评级不得更低 | 4 个下限 × 评分 1..5 |
| P4 | 结果不得低于"该武将所属列表"的危险度（危险列表不能被降级放过） | 20 组 |
| P5 | 多个守军时取最危险的一个 | 含软柿子的组合 |
| P6 | 体力/士气**已识别**且低于门槛时，绝不能被选中 | 168 组，违规 0 |
| P7 | "未验证放行"只出现在确实无法识别的组合上 | 恰好 42 组 |

为什么断言"性质"而不是"具体输出"：性质才是必须成立的东西；
断言某个具体输出只会锁死实现细节。而 P1 里的"推荐语不得含鼓励措辞"
是这个脚本里最有价值的一条——它直接锁住了刚修掉的那个危险行为。

**⑤ 过程小记（两次自查）**：写这个脚本时我又在中文串里嵌了双引号（第三次犯同一个毛病）；
另外 P5 的期望值算法写得又绕又错、P7 的算术也错了（未验证组合应是
`(1×7 + 7×1) × 3 = 42`，我一开始写成 `8×7×3`）。两处都是**跑起来才发现的**。

**⑥ 证据**：一键回归 **11/11** 通过；`SafetyTier.UNKNOWN` 已在唯一那个 `when` 表达式中被显式处理
（该枚举全工程仅此一个文件使用，因此新增值的影响面是闭合的）。

### 3.31 第二十七轮补充：看门狗是"乱点"的源头，而它的配置意图从未生效

`WatchdogRecovery` 是整个工程里**唯一在感知失败时仍然主动点击**的代码，
也就是"乱点"风险的集中地。这一轮枚举它的状态空间，查出两个问题。

**① 问题一：`watchdogKeywords` 的**顺序**从未生效。**
`dismissAnyDialog` 原先这样挑按键：

```kotlin
val bestBtn = matches.maxByOrNull { it.confidence } ?: return false
```

置信度只表示"这几个字读得清楚"，**并不表示"这个按钮按下去安全"**。
而 `watchdogKeywords` 是一个**有序**列表，作者把「确定」放在最前面，
正是在表达"优先按它"——这个意图被完全忽略了。

后果很具体：一个同时有「确定」与「取消」的弹窗里，若「取消」读得更清楚，
它就会去按「取消」，**把用户原本的操作取消掉**。
离线构造的反例（`tools/validate_watchdog_logic.py`）：

```
弹窗上同时有「确定」(置信度 0.71) 与「取消」(置信度 0.97)
  旧实现（按置信度）会按：取消    ← 把用户的操作用消了
  新实现（按知识库顺序）会按：确定
```

现在改为**先按列表顺序，其次才在同一关键词内比置信度**。
这与前几轮修掉的 `threatScore`、`extraTargetsRaw` 属于同一类问题：
**配置里写了意图，代码却从来没有使用这个意图。**

**② 问题二：感知不可用时，它会在"完全不知道屏幕上是什么"的情况下连点 4 次。**
`recoverToMainMap` 的兜底分支对任何未知场景都执行 `tapSafeBlankArea()`。
当 OCR 不可用时，`dismissAnyDialog()` 必然返回 false（它靠读文字找按钮），
于是这条路径就成了**纯盲点**，而且每轮都点一次、共 4 轮。
那个"安全空白点"若正好落在弹窗按钮或列表项上，就会触发非预期操作。

修法：新增 `MAX_BLIND_TAPS_WHEN_PERCEPTION_DEAD = 1`。
允许一次是有道理的（万一只是个能收起的浮层）；
不允许更多——继续盲点已经接近乱点。超预算时**如实中止并说明**：

```
自愈中止：文字识别不可用，无法判断屏幕上是什么；已做 1 次盲点后停止。
请手动把游戏切回大地图，或先用带 ncnn/OpenCV 的构建让识别可用。
```

**③ 而这道闸我第一版放错了位置——是校验脚本把它抓出来的。**
第一版把预算判断放在"未知场景兜底"那一支里。看起来对，
但"已知次级面板"那一支同样会点击，**却绕过了预算**。
离线枚举立刻报出"感知不可用时最坏盲点 4 次"，我才发现。
现在这道闸被提到**所有点击分支之前**——意义是：**以后新增分支也不会绕过它**。

**④ 新增第 12 项回归检查：**`tools/validate_watchdog_logic.py`，8 条性质断言：

| 性质 | 内容 |
|---|---|
| W1 | **必然终止**：迭代不超过 maxAttempts，不存在无限自愈循环（覆盖 36 种组合） |
| W2 | 初始即大地图时**零点击** |
| W3 | 感知不可用时**实际盲点**不超过 1 次 |
| W4 | 只有"最终确认回到大地图"才算成功，不会因"点过了"而返回 true |
| W5 | 读不到文字时 `dismissAnyDialog` 必须返回 false（不猜位置去点） |
| W6 / W6b | 有序表里靠前的关键词优先于置信度更高的靠后关键词，**且旧行为确实会选错** |

W6b 是特意加的：它证明这条修复**不是装饰**——旧行为在该场景下真的会按「取消」。

**⑤ 过程小记（一次自查）**：W3 一度报"实际最坏盲点 2 次"而失败，
查下来是**我校验脚本自己的计数器语义**问题——`blindTaps` 是**预算计数器**
（先自增再判断），所以返回值比"实际点击次数"多 1。
Kotlin 那边的日志写 `blindTaps - 1` 正是这个原因。
现在脚本把"预算用量"与"实际盲点次数"分成两个变量，断言只对后者做。

**⑥ 证据**：一键回归 **12/12** 通过；对照数据：
感知不可用时最坏点击 **1** 次，感知可用时 **4** 次——**乱点被压制**。

### 3.32 第二十八轮补充：把"守军评估"从摆设变成可用的功能

上一轮我报告了一个发现但**没有擅自处理**：`DefenderEvaluator` 与
`EngineBridge.evaluateDefenderPanel` 整套"守军评估"链路**没有任何调用方**。
这一轮把它接上——而且刻意接成**手动入口**。

**① 军师页新增「🛡️ 评估当前守军」。**
点一下就会：按锚点裁出守军名单区 → OCR → 按知识库评级 → 显示
危险度、推荐语、综合风险分、命中守将清单与逐个的克制建议。

**为什么做成手动而不是自动**：它依赖先打开「查看守军」面板。
自动去做会在**错误的界面**读出无关文字——那正是"乱读"的来源。

**② 新增可标定锚点 `DEFENDER_PANEL`（查看守军·武将名单区）。**
默认值是一个**宽松的居中区域**（x 0.12~0.88, y 0.12~0.78），并已加入
「标定」页签的引导式区域标定顺序（⑦ 现在会依次标定三个区域）。
偏大是**有意**的，理由是下面 P8 证明的性质：多圈进来的文字只会让评级**更危险**，
不会让危险守将被降级放过——所以这是偏安全的方向。

**③ 补了两条新性质，正是"区域可以开得偏大"的依据与代价。**
* **P8 噪声只能提升危险度，绝不降低**：枚举 6 组基线 × 3 种追加（含 5 个无关词），
  危险度从不下降。这就是偏大默认值可接受的原因。
* **P9 无关文字被保守记为 MODERATE——代价是 SAFE 判定很难出现**：
  单看「兵力」两个字就会得到 MODERATE。这意味着只要识别区域里混进**任何**无关文字，
  「🟢 推荐立刻收割」这个最有用的结论就出不来。

P9 是一个**有意取舍的副作用**，我把它**如实写出来而不是偷偷改掉**：
改成"无关文字一律忽略"会让评级更容易给出 SAFE，那是**更危险的方向**
（假 SAFE 会推动用户去打一块可能团灭的地）。
正确的应对是**把区域标定准**（这正是新增 `DEFENDER_PANEL` 锚点的意义），
而不是放宽判据。

**④ 证据**：一键回归 **12/12** 通过；决策验证现有 **9 条性质**全部符合预期
（P1–P5、P8、P9 与选队 P6–P7）；守军评估链路符号已逐点核对
（`btnAdvisorEvaluateDefenders` → `UiAnchors.rect(DEFENDER_PANEL)` → `evaluateDefenderPanel`）。

## 9. 定向复读、取证工具与整体收尾复核（第三十 ～ 四十轮）

我无法编译，所以唯一还能降低风险的手段就是**按风险排序，把改动逐一复读**。
这一轮复读了三类：跨文件类型改动、新增枚举值、以及我自己可能引入的 Kotlin 陷阱。

**① 复读结果：两处确认安全，一处揪出潜在风险。**

| 复读点 | 结论 |
|---|---|
| `RectKey` 新增 `DEFENDER_PANEL` 是否需要补 `when` 分支 | **不需要**：全工程没有任何对 `RectKey` 的穷尽 `when`（枚举靠 `values()` 迭代） |
| `WatchdogRecovery` 里的 `-m.confidence` 是否合法 | **合法**：`KeywordMatch.confidence` 是 `Float`，`-Float` 仍是 `Comparable` |
| `OpenCvMatcher` 里的 `Scalar(-1.0)` | **潜在风险，已改**：项目其它地方一律用 3/4 参形式（`Scalar(0.0, 120.0, 100.0)`），而单参/varargs 构造在 OpenCV 各 Java 版本间支持不一致。已改为无歧义的 `Scalar(-1.0, -1.0, -1.0, -1.0)` |

**② 新增一条此前查不出的编译错误类别：同一作用域内重复声明。**
这一路我新增了大量函数，"同名同参数"是真实风险，而现有检查全都覆盖不到。
新规则会解析每个 `fun` 的**参数类型签名**，并按"最近的类 + 最近的成员函数"划分作用域后查重。

关键在于**不许误报**——Kotlin 允许三种容易误伤的情形，我把它们都做成了自测用例：

| 情形 | 期望 |
|---|---|
| 同名同参数 | 报出 |
| 同名**不同**参数（合法重载） | 不报 |
| 同一文件里两个不同类各有 `fun stop()` | 不报 |
| 两个方法里各自声明同名**局部函数** | 不报 |

结果：真实工程 **51 个 Kotlin 文件、0 处重复声明**。

**③ 而这条新规则的自测，立刻抓出了它自己的一个真 bug。**
第一版里我用"**行内索引**"（`mf.end()-1`）去索引**整个文件**的字符串来取参数列表——
位置完全错位，算出来的签名是垃圾，于是"同名不同参数是合法重载"这一条被误报。
修法是同时记录每一行在文件内的起始偏移，再做换算。
**如果我没写这条自测，这个检查会带着"签名恒为垃圾"的缺陷一直绿灯下去**——
它会通过所有测试，因为它把一切都判成重复……除了它恰好没报出来的时候。

**④ 证据**：一键回归 **12/12**；`verify_refs --selftest` 现有 **28 个用例**全部符合预期
（领域不变量 4 / 持久化 3 / 版本号 4 / 只写不读 2 / 界面可见性 3 / 可达性 2 /
具名参数 6 / 重复声明 4）。

### 第三十一轮：继续复读（枚举分派点、签名同步、新对象成员）

**① `GameState` 的分派点全部有 `else` 兜底，不会静默落空。**
逐一核对了 `stateLabel`、`AutoPilot` 主循环、`EngineBridge.waitForState`、
`LicenseGate` 与 `MainActivity` 里那几个 `when`——都带 `else`。
因此将来新增一个 `GameState` 值，会落到"过渡/未知画面"这一支，而**不会**什么都不做。

> **顺带说明我为什么不去做"`when` 穷尽性"的自动检查**：
> Kotlin 对**表达式位置**的 `when` 本来就会强制穷尽，编译器会报错——静态再查一遍没有增量；
> 而**语句位置**的 `when` 允许不穷尽，且"缺一个分支"经常是**有意**的
> （例如 `PickTarget` 的第一个 `when` 只负责应用选点结果，未列出的常量落到空分支是对的）。
> 做一个会误报的检查，只会训练人去忽略它。

**② 把三个新对象纳入成员对账。**
`TemplateMatcher` / `ButtonTemplateStore` / `OpenCvMatcher`——它们的成员调用全部解析到位。

**③ 补上一类此前的盲区：位置实参**个数**。**
成员对账只验证"名字存在"，不验证"个数对不对"——一个调用完全可能用对成员名、
却传了错误的参数个数。现在签名表里额外记录了 `(最少个数, 最多个数)`：
带默认值的参数计入上限、不计入下限；有 vararg 则不设上限；尾随 lambda 也算一个实参。

**④ 这条新检查的三类假阳性，全部出现在检查器里、产品代码一处分问题都没有。**

| # | 假阳性原因 | 表现 | 修法 |
|---|---|---|---|
| 1 | 字符串屏蔽把**引号也抹掉了** | `logWarn("文字")` 变成 `logWarn(      )`，那个实参被数成 0 个 → **一次报出 244 项** | 只抹字符串内容，保留引号 |
| 2 | `_split_top_level` 把 `>=` 里的 `>` 当成闭合尖括号 | 深度被打成负数，后续逗号不再算顶层 → `TroopSlotDetail` 的 8 个具名参数被数成 3 个 | 先跳过 `>=`/`<=`/`->`/`=>`；`<` 仅在紧跟标识符时才算泛型 |
| 3 | 库调用与工程函数**撞名** | `java.util.Calendar.getInstance()`、`okhttp Call.execute()` 去匹配工程里的 `getInstance(context)` → 又报 5 项 | 实参个数检查只对"**工程内限定名**或**同文件声明**"的调用做，并排除一批天生易撞名的库方法名 |

**⑤ 一句必须说明的取舍**：为了不误报，实参个数检查现在**故意跳过**一部分调用
（跨文件的、且被调用者名字属于易撞名清单的裸调用）。这是"安静"换"覆盖"：
我宁可它少查一点，也不愿意它每次报出几十条噪音——**会误报的检查等于没有检查**。

**⑥ 证据**：真实工程 **0 处**实参/具名参数问题；
`verify_refs --selftest` 现有 **35 个用例**全部符合预期
（领域不变量 4 / 持久化 3 / 版本号 4 / 只写不读 2 / 界面可见性 3 / 可达性 2 /
具名参数与实参个数 13 / 重复声明 4）；
其中实参个数相关的 7 个用例钉住了"正好够 / 少给 / 多给 / 有默认值可省 / 尾随 lambda / vararg / 比较运算符干扰计数"。

### 第三十二轮：核对改写过的签名，并修掉一处"标定坏掉但不报错"的隐患

**① 逐个核对"同类型参数"的调用点——这类**顺序传错不会报错**，最隐蔽。**
我把这一路改过签名的几处调用点逐一读了原文：

| 被调函数 | 调用点 | 结论 |
|---|---|---|
| `ButtonTemplateStore.saveFromFrame(type, frame, centerX, centerY)` | 随用随学（具名传参：x 取 left/right、y 取 top/bottom）；标定入口（位置传参 `type, frame, p.x, p.y`） | **两处顺序都正确** |
| `RecognitionHealth.recordButton(type, ok, failureDesc, textBlockCount)` | `StzbUiMatcher` | **顺序正确** |
| `UiAnchors.calibrateRect(key, l, t, r, b)` | 引导式区域标定（传 `min(x), min(y), max(x), max(y)`） | **顺序正确** |
| `OpenCvMatcher.loadTemplateFromBitmap(keyName, bitmap)` | `StzbUiMatcher` | **顺序正确** |
| `TemplateMatcher.search(frame, template, …)` | `StzbUiMatcher`（具名传参） | **正确** |
| `generateAdvisorLiveStream(statusText, activeOrder, patrolRunning)` | 悬浮窗状态回调 | **正确（3 个实参）** |

也就是说**没有发现顺序传错**。这本身是一个结论，不是一个空转的检查。

**② 但发现一处"标定坏掉却不报错"的隐患，已修。**
`UiAnchors.calibrateRect` 原先直接把四个角交给 `clampToCanvas` 就存盘：

```kotlin
rectOverrides[key] = clampToCanvas(Rect(left, top, right, bottom))
```

而 `clampToCanvas` 里的 `right.coerceIn(left + 1, w)` 会把**反向矩形压成 1px 宽的细条**——
不崩、不报错，但那个识别区域**永久失效**：用户看到的现象只是"这块识别不到文字"，
完全查不出原因。这与本项目一贯的"静默失效"是同一类病。

修法两条：
1. **先归一化**（`minOf`/`maxOf`）——用户可能从右下往左上拖选，两个角的先后并不保证；
2. **拒绝过小的矩形**（< 16 设计画布像素）：这种区域同样永远读不到字，
   存进去只会制造一个"看起来已标定、实际无用"的锚点。
   现在 `calibrateRect` 返回 `Boolean`，调用点在被拒时**明确弹提示**
   （"范围太小，未保存，请把两个角拉得更开"），而不是让用户以为标定成功了。

**③ 顺带把一处"没有调用方"的公开方法变成有用的入口。**
`ButtonTemplateStore.clear(type)`（单个清除）此前没有调用方。
我没有删掉它，而是给了它一个真实用途：**⑨ 试匹配结果对话框新增「清除该模板」按钮**——
试匹配失败往往就是模板本身不好（对准偏了、或那片区域几乎纯色），
就地清掉再重新登记，比留着一个"已登记但永远匹配不上"的模板好。

**④ 证据**：一键回归 **12/12**；`calibrateRect` 签名改动的唯一调用点已使用新的 `Boolean` 返回值
（`grep calibrateRect` 全工程仅 2 处：定义与这一处调用）。

### 第三十六轮：把验证脚本"仍复刻"的部分也接到源码上

上一轮列的第二件事：三个 `validate_*.py` 里仍有**复刻**的规则，
它们是最后一处可能漂移的地方。这一轮逐行对照 Kotlin 原文，并把能自动化的部分接上。

**① 逐行核对结果：三处复刻**与 Kotlin 一致**。**
* `findMatch` 的检索顺序：Kotlin 是 **danger → hard → safe → moderate**，
  条件为 `name.contains(hero.name) || hero.name.contains(name)`（双向包含）——与复刻一致；
* `resolveTier`：`if (byScore.weight >= listFloor.weight) byScore else listFloor` ——一致；
* `selectOptimalTroop`：无法识别时**放行但记为未验证**、已识别且不达标则**跳过**、
  循环结束返回 `null` ——一致。

也就是说，**没有发现不一致**。这本身是个结论。

**② 但"顺序"这件事值得单独说：它其实是规则的一部分。**
如果谁把 `safeHeroes` 挪到 `dangerHeroes` 前面，
一个**既在危险表又在软柿子表**里的武将就会按软柿子处理——
这种改动在代码评审里极容易被忽略，后果却是白送兵。

于是我把**顺序**也改成从源码解析：`parse_find_match_order()` 会读出
每个 `for (hero in db.XXXHeroes)` 及其对应的 `resolveTier(SafetyTier.Y, …)`，
实测解析结果 `['danger', 'hard', 'safe', 'moderate']` 与源码一致。

**③ 并新增一条直接守住已修 bug 的断言（P0b）。**
解析 `var maxRiskTier = SafetyTier.X` 后断言：**起始值必须是权重最小的那个评级**。

```
OK | P0b. 聚合起始评级必须是权重最小的那个（守住「空输入不会变成 SAFE」）
     源码起始值=UNKNOWN(权重 0)，最小权重=0（UNKNOWN），比较符=[>]；
     检索顺序=['danger', 'hard', 'safe', 'moderate']
```

这条断言的意义是：**如果将来有人把起始值改回 `SAFE`，
"一个守军都没读到"就会重新变成「🟢 推荐主力立刻出征收割」——而检查会立刻红。**

**④ 看门狗那边同样处理，并且**解析器当场失败了一次**。
把"哪些场景走点空白那一支"的状态表也从源码解析时，第一版正则先匹配到了
`if (currentState == …MAIN_MAP)` 这个**单条件**分支，只解析到 1 个状态。

关键在于：解析器**按设计报错退出了**，而不是拿一个错的值继续跑：

```

```

改成精确匹配"至少一个 `||`"的条件后，解析出
`['TILE_ACTION_MENU', 'TROOP_DISPATCH_DIALOG', 'DEFENDER_INFO_DIALOG', 'COORDINATE_SEARCH_DIALOG']`，
与源码一致。**这就是"响亮的失败"的价值：它把一次静默的错误值变成了一次可见的中断。**

**⑤ 剩下的边界已如实标注在各脚本的输出里**，不再笼统地说"必须同步"：
* 决策脚本仍复刻：聚合的**赋值方式**、选队门槛的**比较结构**
  （阈值来自知识库，运行时取值，无法静态解析）；

  且**关闭词表在运行时会先被知识库的 `watchdogKeywords` 覆盖**（非空时优先），

### 第三十八轮：军师页复核，查出一处会"把你自己的坐标当成军令目标"的缺陷

**① 先把军师页所有文本写入点摸清楚（防止我这些轮次的改动互相覆盖）。**
`tvAdvisorStream` 共 12 处写入、`tvAdvisorMetrics` 6 处，逐一核对后结论是**没有冲突**：

* 四个按钮各自负责自己的用途（军令解析 / 战报会诊 / 无人托管 / 守军评估）；
* 状态回调**只在文本为空时**才写入推演，因此不会抹掉你刚解析出的军令；
* `ensureLicense()` 里那处写入只在授权被拦时触发（默认开放模式直接放行），不影响正常使用。

军令/战报两个按钮的实现也确认是诚实的：都有 `ensureEngineReady()` 前置检查，
抓屏失败、OCR 读不到文字时**中止并说明原因**，而不是拿硬编码样本继续往下走。

**② 但查出一处真实缺陷：整屏 OCR 会把 HUD 里"你自己的坐标"喂进军令解析。**

`EdgeSlmEngine.extractCoordinates` 取的是**第一个**落在 `1..1500` 的坐标匹配：

```kotlin
while (m.find()) {
    val x = ...; val y = ...
    if (x in 1..1500 && y in 1..1500) return Pair(x, y)   // 取第一个
}
```

而军师页喂进去的是**整屏**文本，HUD 右上角显示的又正是**你当前的坐标**，
格式与军令里的目标坐标**完全一致**。于是存在这样一条路径：
**把"你所在的位置"当成"军令里的目标"**。

它不会报错、也不会显得异常——**只会让你跑错地方**。
这正是需求 (4) 里"识别意图不准"的一种具体形态。

**③ 修法：按已知几何把 HUD 读数区域剪掉。**
新增 `semanticTextExcludingHud()`：从 OCR 的 `textBlocks` 重新拼文本，
**丢弃中心点落在 `HUD_WORLD_COORD` 矩形内的块**。军令与战报两处都改用它。

同时把"读不到文字"的提示分成两种情形（不再混为一谈）：
画面里**一个字都没有**，还是**读到了字但全在已排除的 HUD 区域里**。

**④ 这个修法依赖"帧与锚点同坐标系"，而这一点**由既有代码构造性证明**。**
`MapCoordinateSystem.readCurrentCenterWorld()` 正是这样读 HUD 的：

```kotlin
val roi = UiAnchors.rect(UiAnchors.RectKey.HUD_WORLD_COORD)
val bmp = EngineBridge.captureRoi(roi)     // 用虚拟坐标矩形去剪裁捕获帧
```

也就是说**捕获帧本来就是虚拟画布尺寸**，OCR 的 `boxPoint` 与 `UiAnchors` 的矩形
可以直接比较，无需换算。这不是我的假设，而是这块代码一直在用的约定。

**⑤ 仍然存在的边界（如实写明）**：这次只排除了 HUD 那一块。
画面上其它"像坐标"的文字（例如资源栏数字、某些面板里的坐标）没有被排除，
只是靠 `1..1500` 的范围检查挡掉大部分。
若真机上仍出现目标识别错，下一步应当给军令/战报也**各加一个可标定识别区域**——
但那会要求你先标定一次，因此这一轮没有默认启用它。

**⑥ 证据**：一键回归 **13/13**；`grep` 确认 `semanticTextExcludingHud` 有 1 处定义 + 2 处调用
（军令、战报各一处）；坐标系一致性由 `readCurrentCenterWorld()` 的既有用法构造性印证。

### 第三十九轮：点击链路复核，又查出一处"代码与注释不符"导致的点错风险

**① 先验证了一条被声称但没人验证过的边界：抖动幅度。**
`EngineBridge` 声称抖动"控制在 1.0px 以内"，而 `AutoTouchService` 里**又抖了一次**。
读 `KineticTouchEngine.generateJitteredPoint` 确认：半径被 `coerceAtMost(maxRadius)` **真正封顶**，
因此两处各自的声称都成立 ✓；两层叠加最坏约 2.7 真实像素，
对高度通常 ≥40px 的按键可忽略。**这条不是缺陷，但此前从没人核算过。**

**② 然后查出真缺陷：按键选择的规则与注释不符，而注释描述的规则更安全。**

`StzbUiMatcher.matchButtons` 里原先是这样：

```kotlin
// 如果已经找到了当前类型且置信度更高，则跳过      ← 注释
if (resultMap.containsKey(type)) continue        ← 代码：无条件跳过
```

**注释声称"且置信度更高才跳过"，而那个置信度比较从来没有被实现过。**
实际行为是：**谁先被 OCR 读到就取谁。**

这会造成真实的点错，因为按键文案在画面上重复出现很常见。而看 `ButtonType` 的定义就更清楚：

* `SCOUT_DEFENDERS`（查看守军）的别名里含**很泛的「查看」**——
  列表里的「查看详情」可能抢在按钮「查看守军」之前被选中；
* `CONFIRM`（确定）的别名里含**「出征」**——它可能与 `ATTACK`（主词就是「出征」）互相干扰。

**③ 修法：按匹配质量择优（同级仍取先出现的）。**

| 质量 | 含义 |
|---|---|
| 3 | 与 `primaryKeyword` **完全一致**（最具体的信号） |
| 2 | 与某个 **alias 完全一致** |
| 1 | 仅**包含** primaryKeyword 或某个 alias |

这样「查看守军」会优先于「查看详情」，「确定」会优先于别名「出征」。
同时**有多个候选时把"到底选了哪一个"写进日志**——这类选择我在本机无法验证，
只能靠真机日志回溯，所以必须让它可诊断。

另外把已无调用方的 `matchesType()` 删掉了（按本项目"死代码要删"的标准，
留着一个二分判断会让人误以为"择优"还有第二个实现）。

**④ 仍然存在的风险（如实写明）**：当画面上**没有**更具体的候选时，
`CONFIRM` 仍会落到别名「出征」上——这在出征面板里通常是**对的**（那个按钮本身就是出征），
但若某个界面同时存在多个同为"质量 2"的候选，规则会退化为"取先出现的"。
真机上遇到点错时，请查这条日志：

```
按键 [CONFIRM] 在画面中有 2 个候选文案（确定 / 出征），
已按「完全一致优先、其次取先出现」选中: '确定'
```

**⑤ 证据**：一键回归 **13/13**；`grep` 确认 `matchesType` 已无残留（只剩说明性注释）、
`matchQuality` 有 1 处定义 + 1 处调用。

### 第四十轮：真机截图到位——两项"只能真机验证"的检查第一次真跑，并据此补上模板匹配的亚格精修

用户提供 21 张 `2712x1220` 真机截图。此前 `scene-fingerprint` 与 `template-matcher`
两项在回归里长期是 **SKIP**（"没有截图所以没跑过"），这一轮第一次拿到真机数字。

**① 场景指纹（`recoverToMainMap` 唯一的安全网）：真机成立。**

| 检验 | 真机结果 |
|---|---|
| 同一张图自比 | 距离 **0** |
| JPEG q75 重压缩后再比 | 距离 **0~1**（压缩不破坏指纹） |
| 同一 UI 的两个变体（大地图 ↔ 大地图） | **4/5 区域命中**（阈值 0.6 → 判为大地图，正确） |
| 4 张完全不同的界面（战报 / 封控建筑 / 主城 3D / 部队总览） | 全部 **0/5**，区域距离 **24~44** |

正负例之间有一条很宽的沟（5~6 对比 24~44），判据可以放心。
顺带量到一个此前不知道的事实：底部第 5 张卡的文案会在 **「国家」与「同盟」之间变化**
（取决于玩家当前状态），所以那一个区域**本来就不可靠**——
这正是 `MIN_MATCH_RATIO=0.6`（5 个里对 3 个即可）而不是"全对"的理由。
若当初写成"5 个全中"，这个指纹在真机上会时不时失灵。

**② 模板匹配：先抓到两个**夹具**的假结论，再量出一个**算法**的真缺陷。**

夹具的问题（这类问题的恶劣之处在于它会报出看起来很像算法失败的 FAIL）：
* 帧框与模板框写死成绝对像素 `1100,700,700x460`，只有 ≥1800x1160 的图装得下；
  1080 高的截图会被 PIL 用**黑边补齐**，模板裁在空白上 → 分数 0.4 的假 FAIL。
  现按图片尺寸取比例，并加"模板灰度标准差 <3.0 就直接报夹具不行"的自检。
* 模板边界必须落在 4x4 块网格上（对齐 `ALIGN=4`）：半格处裁出来的模板
  与帧的块网格错开 2px，同内容也对不齐，用例 ① 会假失败。

算法的真缺陷（这次是算法本身，不是夹具）——**降采样块网格的相位损失**：
`toGray` 从**各自 Bitmap 的 (0,0)** 起做块平均，所以"事先裁好的模板 PNG"与"当前这一帧"
的块网格之间有 0..3px 的**随机相位差**。真机三张界面实测：

| 模板裁法 | ZNCC | 离 0.85 阈值的余量 |
|---|---|---|
| 边界对齐块网格 | **1.0000** | 充足 |
| 只偏移 (1,2)px | **0.8646 / 0.9293 / 0.9495** | 最坏 **0.0146** |

而同一批截图上**跨界面负例**最高分是 **0.6674**（另一组 0.6551）。
这两个数字放一起就封死了"把阈值调低点"这条路：**相位损失和真实不匹配落在同一段分数区间里，
降阈值会同时放过负例**。唯一正确的处置是**亚格精修**——
在降采样最佳位置邻域内，按原分辨率把 (2·scale−1)² 个偏移都复算一遍 ZNCC 取最高。

**③ 落地：`TemplateMatcher.search()` 增加 `refinePhase()`，Python 侧同构实现作可执行规格。**
* 门控 `refineBelow=0.95`：对齐相位的真命中本来就 ≈1.0，不为它们付额外代价；
  成本按用例几何估算是粗搜的 3~4%（粗搜 23408 个位置，精修 49 个）。
* 内存上刻意**只截候选邻域**而不是整帧：整帧 `getPixels`+双精度在 2712x1220 上要握住约 40MB，
  邻域版约 0.2MB。
* 精修成功后中心按**原分辨率**算；runnerUp 仍来自未精修的网格（KDoc 写明这会让区分度略偏乐观，
  以及为什么不对次高位逐个精修）。
* 主通道 `OpenCvMatcher`（`TM_CCOEFF_NORMED`）在全分辨率滑窗，**不存在**这个问题，无需改动。

**④ 我自己在这轮犯的一个错，值得单独记：新写的边缘用例 ⑦ 当时是"PASS"，但其实什么都没测。**
⑦ 是把模板裁在帧的右下角（非对齐相位），用来覆盖"邻域被帧边界夹掉一侧"的分支。
首跑三组全绿，但两组的打印是 `精修前=0.9583 → 精修后=0.9583` ——
**默认的 0.95 门控让这些图直接跳过了精修**，用例看着过了、要覆盖的分支一次都没执行。
现在 ⑥⑦ 强制 `refine_below=1.0` 并把 `refined==true` 也写成断言，
这样"没走精修"会直接判 FAIL 而不是安静地绿。
> 这条教训是通用的：**用默认门控去测门控后面的代码，绿灯是假的。**

### 第四十一轮：视觉通道的三件实事——长宽比几何、"用一次就废"的位图缺陷、模板种子

结论先说：模板库与阈值这两件事在本地能真解决的**已经解决，不需要你操作手机**；
OCR 那条本机编不了 ncnn/OpenCV，但我把它"第一次跑 CI 必然踩的坑"查出来并修掉了，见小节 ⑤。

**① "阈值只在校过的机器上成立"——这句话一半是假的，一半是真坑，已修**

先量化"换分辨率要不要重校"。`CoordinateTransformer.refreshMetrics()` 里 virtualHeight **恒等于**
BASE_HEIGHT(720)，virtualWidth = `roundToInt(720 * physW / physH)`，所以 2712x1220 的真实画布是
**1601x720**（过去文档里写的 1600 是抄了参考值，不是实测）。这意味着**纯分辨率变化在数学上已经被
"按高归一化"吸收了**，不需要重校。

真正会让指纹失效的是**长宽比**。旧 `regionRect` 把区域的 x 按"画布宽的比例"算，长宽比一变整条 x 轴平移。
实测（同一张 2712x1220 截图，只改画布宽度）：

| 画布宽度（人为改动的自变量） | 按高折算（新口径）距离 | 按宽比例（旧口径）距离 |
|---|---|---|
| 1280 | 0 0 0 0 0 | 33 46 21 21 31 |
| 1440 | 0 0 0 0 0 | 28 36 35 47 46 |
| 1520 | 0 0 0 0 0 | 13 17 31 33 38 |
| 1584 | 0 0 0 0 0 | 6 4 10 4 7 |

> 表里 1584 那一行 5 个数字都 ≤10，即旧口径在这一档**不会**判错——闸门仍让它 PASS，
> 因为它检查的是"重录基准后正负例能否分开"，不是"旧口径必须失败"。

阈值是 10（单区域距离 ≤10 算命中）。旧口径下 1280 / 1440 / 1520 三档**五个区域全部越界**，
指纹当场判"不是大地图"，表现就是"换台手机场景识别全灭"。
新口径固定 `REF_CANVAS_WIDTH = 1600f`，x 一律按高折算，于是四档 sweep 的按高距离恒为 `[0, 0, 0, 0, 0]`。

改了几何就必须作废旧基准，所以 `GEOM_VERSION` 升到 2：存盘版本不符 → 基准作废 +
`needsRecalibration` + `describe()` 明确告诉你"要重录"，不假装还能用。
这里有个我差点写错的细节：我原本准备在注释里写"新旧口径哈希完全一致，所以旧基准不用作废"，
**自己的探针把这句话推翻了**——同一台机器上框最多错开 1px，但 5 个区域哈希实际差 **0/0/1/4/2** 位
（3 个区域不同），只是都小于阈值 10 才看起来没事。换个长宽比就是上表那种 20~46 位，
而且**无法从哈希反推这份基准是在哪种长宽比下录的**，所以"一律作废"是这里唯一诚实的选择。

**② 顺带修掉一个产品级缺陷：模板命中一次之后，那个按键永远点不到**

`StzbUiMatcher.matchButtonByTemplate()` 的 `finally { tpl.recycle() }` 回收的是
`ButtonTemplateStore` **缓存里那一份**位图。第一次模板命中之后缓存对象即失效，
之后每帧 `load()` 拿到的是已回收位图 → 抛异常 → 被 `catch` 咽掉 → 该按键**再也定位不到**。
用户看到的现象就是"这个键登记过、也成功点过一次，然后就再也不干了"。
修法是不再回收（API 26+ 位图在 Java 堆上，交给 GC），并把所有权规则同时写进两侧注释。

**③ "全新用户模板库是空的"——机制层通了**

新增第三种来源：随包种子 `assets/templates/<gameId>/seeds/<ButtonType>.png`，
`ButtonTemplateStore` 现在是本机登记优先、种子兜底，来源用 `Source{NONE,USER,SEED}` 区分；
悬浮窗的登记对话框与试匹配详情改成**三态显示**（本机已登记 / 随包种子 / 未登记），
免得你把种子当成"我自己录的"而覆盖不掉。`registeredTypes()` 只数 USER，种子不会冒充用户成果。

同时补上**模板命中自愈刷新**（`refreshTemplateIfConfident`）：命中分 ≥0.92 才考虑，
每个按键 10 分钟节流，重裁后先用更严的纯 Java 全图搜做自检（≥0.95 且落点在原位 ±8px 内）
才回写。这条路的意义是**让"匹配成功"本身也能积累模板**，不必再等 OCR 先成功一次——
`learnTemplateIfPossible` 的判据也从 `has()` 改成 `sourceOf() == USER`，否则种子会永久占位、
让随用随学看起来"已经学过了"。

配套的生成与验收工具是新写的 `tools/gen_button_seeds.py` + `tools/button_seeds.json`，
五段验收：对比度 → 唯一性自检 → 跨帧可迁移 → 别的界面不误命中 → 与已入包那份逐像素对账
（最后一段专治"清单改了、包里的图没改"）。匹配数学直接复用闸门 14 的 `search()`，
对比度下限与裁剪尺寸一律从 Kotlin 解析，脚本不许有第二份常量。

**① 一个真实 UI 语义推翻了我上一轮的验收判据：地块动作轮盘是浮动的**

它跟着被点的那块地走。同一枚「出征」键，在 `f5531bad` 里落点 (1219,361)，在 `ab67ba1a` 里落点

于是判据按 `anchor` 分两种，写进 `tools/button_seeds.json` 与生成器：

| anchor | 适用 | 跨帧判据 | 实测 |
|---|---|---|---|
| `fixed` | 底栏、出征确认面板等屏幕固定面板 | 落点 ±12px | CONFIRM 偏移 4px、RECRUIT 2px、JUMP 0px |
| `floating` | 地块动作轮盘 | 只要求分数 ≥ 0.90，落点偏移照实打印但不作判据 | ATTACK 0.945（偏移 102px 放行） |

这是**放宽**，所以我把它做成显式字段而不是偷偷改常量：清单里没写 `anchor` 一律按 `fixed` 判。

### 怎么判断这些检查可信

三条自我约束，你可以据此判断我有没有在自说自话：

1. **几乎每条规则都有反例自测**——故意注入缺陷并断言能被抓到。
   其中 `native-ocr` 的第一版自测就暴露出它 **5 个缺陷只捕到 1 个**，随后重写。
2. **凡是"检查器说 OK"但我发现它其实什么都没查的，都当场修的是检查器**，不是改产品代码去迁就它
   （见第 23 节：具名参数检查第一版报出 41 项**全是自己的假阳性**）。
3. **每一项都写明未验证的边界**（上表第五列），不把"静态通过"说成"功能正常"。

### 这份清单**不能**替代什么

* **真实的 Gradle/NDK 编译**：本机无 JDK / Android SDK / NDK / 外网，我一次都没编译过。
* **真机行为**：转屏精度、模板命中率、压秒真实迟到量、识别区域标定准确度。
* **CI 的实际执行**：三个工作流都只做了结构与静态校验。
