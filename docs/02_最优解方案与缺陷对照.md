## 一、APK 体积的真实构成（实测，非估算）

### 1.1 已发现的体积 bug：ABI 未裁剪

`build.gradle:21` 配了 `abiFilters 'arm64-v8a'`，但**该配置只过滤本项目 jniLibs，不处理 AAR 内的 so**。
实测两个 AAR 解压后体积：

| AAR | 压缩包 | 解压后 | arm64 需要 | **纯浪费** |
|---|---|---|---|---|
| `com.quickbirdstudios:opencv:4.5.3.0` | 51.5 MB | **132.8 MB** | 22.3 MB | **110.5 MB** |
| `com.microsoft.onnxruntime:onnxruntime-android:1.22.0` | 27.2 MB | **72.4 MB** | 17.5 MB | **54.9 MB** |

OpenCV 明细：x86_64 55.8MB + x86 40.3MB + armeabi-v7a 13.9MB + arm64 22.3MB。

**不修的话 APK 有 165MB 是纯 x86 死代码，直接吃掉全部预算。**

### 1.2 另一处浪费：OpenCV 拉了两个来源

- Gradle：`com.quickbirdstudios:opencv:4.5.3.0`（AAR，132.8MB）
- CI：又下载完整 OpenCV 4.9.0 SDK（`opencv-4.9.0-android-sdk.zip`）供 CMake链接

而实测代码只用到了两个模块：

```
opencv2/core.hpp    ocv_lite + yolo 共用
opencv2/imgproc.hpp cvtColor / resize / warpPerspective / findContours 等 27 个符号
```

`imgcodecs` / `videoio` / `dnn` / `ml` 等重模块**一个都没碰**。
应二选一（推荐保留 AAR，删掉 CI 的 SDK 下载），并裁剪到这两个模块。

## 二、200MB 预算下的最优组合

### 2.1 为什么不上VLM（硬数据）

| 模型 | 最小可用体积 | 与 200MB 的关系 |
|---|---|---|
| Qwen3-VL-2B Q4_K_M | 1.5 GB | **7.5× 超限** |
| Qwen3-VL-2B Q4_0 | 1.39 GB | 7× 超限 |
| MAI-UI-2B NF4 | 1.57 GB | 7.9× 超限 |
| SmolVLM-500M | ~600 MB | 3× 超限 |
| Moondream 3（9B MoE）| 需 24GB GPU 跑完整版 | 不可行 |

手机实测延迟（官方/第三方面试数据）：

| 模型 | 设备 | 指标 |
|---|---|---|
| Qwen3-VL-2B Q4_K_M | vivo X300 | **30.87 tok/s，首 token 3239 ms** |
| Qwen3-VL-2B | 骁龙 8 Gen 3 | 端到端一问一答 **15~20秒** |
| Qwen3-VL-2B Q4_0 | 骁龙 8 Elite | 40.2 tok/s（CPU，IQ4_NL） |

**结论：200MB 内不存在任何能"理解战局"的通用模型。这不是取舍，是物理约束。**

### 2.2 专用小模型分工（这才是正解）

「理解战局」不需要通用智能，需要的是**感知 + 结构化 + 语义检索 + 模板决策**四件事，
每件都有远小于 VLM 的专用解法：

| 能力 | 方案 | 体积 | 延迟 | 为什么够用 |
|---|---|---|---|---|
| 看见有什么 | YOLOv8s ncnn INT8 | 14 MB | 55 ms | 11类目标检测，专用模型在这项上吊打 VLM |
| 读出文字 | PP-OCRv4 det/rec/cls | 13 MB | 25 ms | 专用 OCR 比 VLM 读字更准更快 |
|理解语义 | bge-small-zh INT8 | 30 MB | <20 ms | 512维向量检索，"三级地怎么打"→ 守军天梯 |
| 理解指令 | rbt3 → INT8 双头 | 20 MB | <50 ms | 意图 + 槽位，输出受约束 DSL |
| 状态建模 | **纯 Kotlin 场景图** | 0 KB | <5 ms | 见 §3.1 |

### 2.3 预算分配（总计124MB，余量 76MB）

| 项 | 体积 |
|---|---|
| DEX + Kotlin + 资源 | 8 MB |
| OpenCV（arm64 +仅 core/imgproc） | 22 MB |
| ONNX Runtime（arm64） | 17 MB |
| OCR v4 三件套 + 字典 | 13 MB |
| YOLOv8s ncnn INT8 | 14 MB |
| bge-small INT8 + 词表 | 30 MB |
| 意图槽位 INT8 + 战法索引 | 20 MB |
| **合计** | **124 MB** |

余量 76MB 用于：真机标定数据、打包冗余、后续 OTA 差分。

## 三、场景图：当前最缺的一层（0KB 代码，最高杠杆）

### 3.1 现状问题

现在的链路是：

```
OCR 读出「出征」→ 字符串硬匹配 → 点击
```

缺的是**中间判断**：这是哪个界面？出征面板开了吗？目标是谁？点完会去哪？

诊断报告 §2.2 显示，`EdgeSlmEngine.kt` 里`myTroopLoss = 2300`、`enemyTroopLoss = 6800`、
`confidence = 0.96` 是**硬编码常量**，`isModelWeightLoaded` 被赋值后零读取。
也就是说系统「知道」战损数值，但那是写死的，不是感知出来的。

### 3.2 场景图要做什么

纯 Kotlin 数据结构，每帧从检测框 + OCR 文本重建：

```kotlin
data class SceneGraph(
    val scene: Scene,              // 出征面板 / 大地图 / 城内 / 战报页 / 未知
    val buttons: Map<UiRole, Rect>,// 出征/驻守/撤退/确定/取消 → 屏幕矩形
    val troops: List<Troop>,       // 我方/敌方部队：坐标、兵力、状态
    val tiles: List<Tile>,         // 地块：等级、类型、归属
    val marchLines: List<MarchLine>,// 行军路线：起点、终点、预计到达
    val unknownObjects: List<Rect> // L1 检测到但无对应类的 → 触发未知界面处理
)
```

**它带来的三个质变**：

1. **点击有前提**：`buttons[UiRole.CONFIRM]` 不存在就不点，而不是盲点+固定延时（P5的根治）
2. **战损是真值**：从 `troops` 的兵力差算，而不是 `2300 / 6800` 常量
3. **未知界面可处理**：`unknownObjects` 非空 → 走模板匹配登记新界面，而不是静默失败

### 3.3 为什么这一层优先级最高

- 不增加任何 APK 体积（纯代码）
- 不需要任何模型（现有 OCR + YOLO 输出即可喂给它）
- **立刻让已下载的 OCR v3 权重价值翻倍** —— 现在读出来的字只能硬匹配，有了场景图才能理解上下文
- 是所有 4个战术 Flow（RoadPaving / ImmunityBreak / SiegeSync / RaidDefense）共同的输入

## 六、被否决的方案（附理由）

| 方案 | 否决理由 |
|---|---|
|端侧 VLM（Qwen3-VL / MAI-UI / SmolVLM） | 最小 600MB，200MB 内物理不可行 |
| 云端 API | 违反「端侧纯离线」前提，且游戏时延不可接受 |
| YOLO26 | CPU 更快、STAL 优化小目标，但 native 解码器写死 v8 布局（`dims=2`、`w=4+nc`、必须有 NMS），切换需重写 `YoloNcnn.cpp` |
| YOLO-World 开放词汇 | 概念优雅，但 ncnn 导出格式不成熟，端侧落地风险高 |
| Moondream 3 | 9B MoE，需 24GB GPU；BSL 1.1 许可非 Apache |
| RT-DETR | 手机 CPU 300~700ms，且无成熟 ncnn 路径 |
| 训千类大模型 | 1500 张标注远不够，必过拟合 |
| 直接用 v8n 省体积 | 11 类里 9 类是小目标（20×20 红点/红线），nano 的小目标短板会漏检按钮 —— 误点「取消」比多20ms 延迟代价高得多 |
