## 1.2 根因归纳（三类）

**根因 1：缺乏「落地即校验」的机制。**
P0 空桩假成功、X/Y 缩放偏差、ABI 未裁剪 —— 三者都是「代码能编译、运行不报错、但结果是错的」。
共性：**没有任何一道关卡在运行期/构建期拦截它们**。空桩曾经 `return TRUE` 骗过了所有人，
ABI 的 165MB 死代码至今没人发现，因为它们都不报错。

**根因 2：把「能跑」当「能用」。**
「击发成功」不看返回值、「OCR 识别成功」是空文本、战损是写死的常量 —— 都是把状态输出
当成了功能完成。**缺少「结果验证」这一环**。

**根因 3：能力与宣传脱节。**
白皮书写「185MB 满血四位一体 AI」，实际是 12.83MB 的 OCR + 一堆不存在/伪造的权重。
技术团队（你）和材料（白皮书）各自为政，没有「以代码为准」的单一事实源。

# 二、完整解决方案（含落地要点）

按「依赖关系」分四阶段执行。**阶段 A 不需要你任何数据，当天可完成。**

## 阶段 A —— 止血（当天，1~2 小时）

### A1. 修 ABI 裁剪（消除 165MB 浪费）★ 最紧急

`client/app/build.gradle` 的 `packagingOptions` 改为：

```groovy
packagingOptions {
    jniLibs {
        useLegacyPackaging = true
        // abiFilters 只过滤本项目 jniLibs，不管 AAR 内的 so，必须显式排除。
        excludes += [
            "**/x86/**", "**/x86_64/**",
            "**/armeabi/**", "**/armeabi-v7a/**"
        ]
    }
}
```

**落地要点**：改完 `assembleRelease` 后用 `unzip -l app-release.apk | grep -c "x86"` 验证应为 0。
预期收益：OpenCV 从 132.8MB → 22.3MB，ORT 从 72.4MB → 17.5MB，**共省约 165MB**。

### A2. 收敛 OpenCV 单来源

现状：`build.gradle:112` 引 `com.quickbirdstudios:opencv:4.5.3.0`，CI 又下载完整 OpenCV 4.9.0 SDK。
实测代码只用 `opencv2/core.hpp` + `opencv2/imgproc.hpp`（27 个符号），
`imgcodecs`/`videoio`/`dnn`/`ml` 一个都没碰。

**落地要点**：二选一 ——
- **方案①（推荐）**：保留 AAR，删除 CI 里的 OpenCV SDK 下载步骤（`build_apk.yml` 的 `Provision OpenCV`），
  CMake 改为只用 AAR 里的头文件（`core` + `imgproc`）。
- **方案②**：保留 SDK 但裁剪模块，链接时只留 core/imgproc。

### A3. 修 B1 —— 世界坐标贯通（根治「点在屏幕中间」）

`DualTrackSafetyGate.dispatchToPipeline()` 的 `targetPoint` 现在是 `屏幕中心`。
改为：**若 `order.targetCoord` 有效，走 `CoordinateTransformer` 世界坐标 → 屏幕坐标；无有效坐标则「如实中止」**。

落地要点：
```kotlin
val targetPoint: PointF? = order.targetCoord?.let { (wx, wy) ->
    MapCoordinateSystem.worldToScreen(wx, wy)  // 用标定好的「每格像素数」换算
}
if (targetPoint == null) {
    callback?.onOrderRejected(order, "军令未含有效世界坐标，无法定位，已中止（不再盲点屏幕中心）")
    return false
}
```

### A4. 修 B2 —— 加旋转监听

`CoordinateTransformer` 已支持 `refreshMetrics()` 重算，但全仓库无调用点。

落地要点：在 `ScreenCaptureService` 或 `MainActivity` 注册 `ComponentCallbacks`（`onConfigurationChanged`），
转屏时调 `CoordinateTransformer.refreshMetrics()` + 重算捕获面。这是「转屏后坐标永久失配」的根治。

### A5. 体积门禁接 CI（改上限 200MB 并强制）

`verify.yml` 已有 `check_assets.py` 步骤，但上限写死 185MB（`check_assets.py:41 DEFAULT_CAP_MB = 185.0`）。

落地要点：
1. 把默认上限改为 **200MB**（与你的底线一致）；
2. `check_assets.py` 增加「APK 最终体积」检查项：构建产物 apk 若 >200MB 直接失败；
3. CI 里加 `--cap-mb 200` 显式传参。

### A6. 修正白皮书假数据

`白皮书.md` 三处（L14、L130、L152-153）写着「185.47MB / 194,477,273 字节 / 内嵌 162MB 模型」，
全部是伪造权重时代的数字。改为实测值：**当前 APK 约 55MB（裁剪后），全引擎就绪约 124MB**。

## 阶段 B —— 场景图 + 真能力（本周，无需截图）

### B1. 场景图构建器（最高杠杆，0KB 代码）

这是「理解战局」的核心，也是当前工程最缺的一层。新增一个纯 Kotlin 类：

```kotlin
data class SceneGraph(
    val scene: Scene,              // 出征面板 / 大地图 / 城内 / 战报页 / 未知
    val buttons: Map<UiRole, Rect>,// 出征/驻守/撤退/确定/取消 → 屏幕矩形
    val troops: List<Troop>,       // 我方/敌方：坐标、兵力、状态
    val tiles: List<Tile>,         // 地块：等级、类型、归属
    val marchLines: List<MarchLine>,
    val unknownObjects: List<Rect> // L1 检测到但无对应类 → 触发未知界面处理
)
```

**落地要点**：每帧从 `YoloDetector` 检测框 + `OcrManager` 文本重建。带来三个质变：
1. **点击有前提**：`buttons[CONFIRM]` 不存在就不点（根治 A4 的残留与 P5 类问题）；
2. **战损真值**：从 `troops` 兵力差算，替代 `EdgeSlmEngine.kt:180-181` 的写死常量（修 C3）；
3. **未知界面可处理**：`unknownObjects` 非空 → 走模板匹配登记，而不是静默失败。

### B2. 修 C3 —— 战损常量替换

`EdgeSlmEngine.diagnoseBattleReport()` 里 `myTroopLoss = 2300`、`enemyTroopLoss = 6800` 是硬编码。
改为从场景图的 `troops` 实测，或从战报 OCR 文本中解析兵力数字（OCR v4 上线后）。

### B3. 修 C4 —— OCR v4 转换入包

基座已下载（`.models/ocr/`），脚本已就绪（`tools/p1/onnx2ncnn.py`）。
转换 det/rec/cls 三件 → ncnn，落 `assets/ch_PP-OCRv4_*_infer.{param,bin}` + 字典。
收益：率土生僻字/书法国名识别率提升，这是当前唯一真跑的引擎，改了立刻见效。

## 阶段 C —— 训练（需你截图，3~5 天）

### C1. YOLO v8s 11 类训练（修 C1）

这是最大的能力缺口：5 个 UI 按钮类（出征/驻守/撤退/确定/取消）几何通道**根本找不出来**。

落地要点（详见 `tools/train_yolo/README.md`）：
- 采集：每类 ≥200 张、总 ≥1500 张，覆盖不同分辨率/昼夜/季节/界面状态；
- 训练：`python tools/train_yolo/train.py --weights yolov8s.pt --epochs 200 --imgsz 640`；
- 导出：`yolo export format=ncnn` → `yolov8n_stzb.{param,bin}` 入 `assets/models/`。

**为什么 v8s 而非 v8n**：11 类里 9 个是小目标（20×20 红点/红线），nano 小目标短板会漏检按钮，
误点「取消」比多 20ms 延迟代价高得多。

### C2. RAG 索引重建（修 C2）

现状 21KB 假索引（31 条、64 维哈希向量）。改抓公开 wiki 语料 → bge-small-zh 算向量 →
`tools/p1/build_rag_index.py --mode bge` 建真实 HNSW 索引。

# 三、防复现保障机制

## 3.1 三道自动闸门（防「能跑但错」）

| 闸门 | 机制 | 拦截什么 |
|---|---|---|
| **构建期** | `check_assets.py` 体积门禁 + ABI 检查 | ABI 未裁剪、体积超 200MB、假权重（0字节/非魔数） |
| **运行期** | `CoordinateTransformer.selfTest()` 已存在，扩展为每次点击前校验 | 坐标映射失效 |
| **CI 期** | `run_all_checks.py` 14 项静态检查 + `check_ci_shell.py` | 引用了不存在的资源/模型、shell 结构错误 |

**关键经验（必须固化）**：本项目历史上三次「假成功」都是「绿灯但结果是错的」——
① bash 管道没 pipefail 屏蔽 Gradle 失败；② OCR 空桩 return TRUE；③ `model-bases` 的 skip_reason 写死。
**通用教训：任何「就绪/成功」的判定，都必须校验「结果本身」而非「状态输出」。**

## 3.2 单一事实源

- 能力以**代码为准**，文档只能描述代码。改代码必同步改文档（`02` 文档已建立对照表）。
- 白皮书是营销材料，与代码事实源分离，发布前必须 diff 一次（A6 落地）。

## 3.3 体积预算冻结

`check_assets.py --cap-mb 200` 进 CI 后，任何依赖膨胀或误塞 x86 so 都会**构建失败**。
这是「杜绝 ABI 问题再次出现」的硬保障。

## 3.4 能力状态如实化

`ModelAssetManager` 已有「诚实报告」机制（YOLO/OCR/RAG/SLM 四能力如实标注「真推理/几何回退/不存在」）。
**保留并扩展**：场景图接入后，新增「战局理解」能力状态，同样如实报告是「模型理解」还是「规则模板」。

# 四、商业化实施路径

## 4.1 分阶段发布策略

| 阶段 | 目标 | 关键动作 |
|---|---|---|
| **内测**（1~2 周） | 验证功能真跑通 | 阶段 A+B 完成，OCR 真推理、场景图上线；`DEVELOPMENT_MODE_OPEN_ACCESS` 仍 `true` |
| **小范围灰度**（2~4 周） | 验证授权链路 | 阶段 D1 完成，卡密激活全流程；10~20 个种子用户 |
| **正式商业发布** | 收费 | 阶段 C 完成（YOLO 权重），功能完整 + 付费墙 + 防封验证 |

## 4.2 商业可行性的三个前提（缺一不可）

1. **功能真实**：OCR 真推理 + 场景图 + YOLO 权重。否则「理解战局」是假话，客户必退款。
2. **付费墙有效**：`LicenseGate` 关闭开发模式 + 真实 Supabase 鉴权 + 卡密去重校验。
3. **防封可靠**：这是率土外挂类工具的**生死线**。`StealthEnvironmentManager` + 高斯抖动 + OLLVM 已具备，
   但需真机灰度验证，不能只靠代码审查。

## 4.3 合规风险提示（必须正视）

这是游戏辅助工具，存在账号封禁与游戏运营方投诉风险。商业落地前建议：
- 明确用户协议与免责声明；
- 卡密定价与退款政策清晰（避免投诉与法律纠纷）；
- 评估目标市场对「自动化辅助」的接受度（部分平台明令禁止）。

**建议**：如果目标是长期商业运营，优先考虑把核心能力包装成「辅助决策工具」（战报分析、军令解析、
配将建议）而非「全自动托管」，前者合规风险显著更低，且正好是你的 RAG + 场景图 + bge 能交付的价值。
