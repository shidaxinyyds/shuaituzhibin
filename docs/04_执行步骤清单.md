## 阶段 A —— 止血（6 步，当天完成，不需要任何数据）

### 步骤 1：ABI 裁剪（消除 165MB 死代码）★ 最重要，最先做

**文件**：`client/app/build.gradle`（第 81-85 行的 `packagingOptions`）

**改法**：`packagingOptions` 里加 `excludes`：

```groovy
packagingOptions {
    jniLibs {
        useLegacyPackaging = true
        excludes += [
            "**/x86/**", "**/x86_64/**",
            "**/armeabi/**", "**/armeabi-v7a/**"
        ]
    }
}
```

**为什么必须做**：`abiFilters 'arm64-v8a'`（第 21 行）只过滤本项目自己的 jniLibs，**不管 AAR 里的 so**。
实测 `com.quickbirdstudios:opencv:4.5.3.0` 解压后 132.8MB（x86_64 独占 55.8MB），
`onnxruntime-android` 72.4MB。不排除的话，165MB 纯 x86 死代码会直接吃掉全部预算。

**验证**：CI 构建后 `unzip -l app-release.apk | grep -c "x86"` 应为 0。

### 步骤 2：核实并收敛 OpenCV 双来源

**背景**：代码里 OpenCV 有两个来源，且用途不同，需先核实再决定删哪个：
- `build.gradle:112` 的 `com.quickbirdstudios:opencv:4.5.3.0`（AAR）→ 提供 `libopencv_java4.so`，供 **Java 层**调用；
- `build_apk.yml:76-93` 下载的 OpenCV 4.9.0 SDK → 供 **CMake 编译 native 层**（ocr_lite + yolo 用 `core.hpp`/`imgproc.hpp`）。

**改法（分两步判断）**：

1. **先核实 Java 层是否用了 OpenCV**：
   ```bash
   grep -rn "org.opencv\|MatOfPoint\|Imgproc" client/app/src/main/java/
   ```
   - 若**无输出**（Java 层没用 OpenCV API）→ AAR 是纯浪费，可删。
   - 若**有输出** → AAR 必须保留，只做步骤 1 的 ABI 裁剪。

2. **native 侧 SDK 保留，但确认只链接 core/imgproc**：代码实际只用 27 个符号（`cvtColor`/`resize`/`warpPerspective`/`findContours` 等），全部在 core + imgproc 内，无需裁剪 SDK 本身（构建期不会打进去），只需确认 CMake 没链接 imgcodecs/videoio/dnn。

**验证**：APK 体积应显著下降；`libopencv_java4.so` 若 Java 层不用则不存在，native 侧正常编译。

### 步骤 3：修复世界坐标丢弃（拆掉定时炸弹）

**文件**：`client/app/src/main/java/com/stzb/assistant/ai/decision/DualTrackSafetyGate.kt`

**背景**：`dispatchToPipeline()` 第 131-133 行仍把 `targetPoint` 写死成「屏幕中心」。
虽然这个类当前不在调用链里（已被绕过），但它留在代码库里，将来一旦重新启用就会复发。
而且 `MapCoordinateSystem.worldToScreen()` 已经是现成的正确换算。

**改法**：`dispatchToPipeline()` 开头改为：

```kotlin
// 用军令里的世界坐标换算屏幕坐标；无有效坐标则如实中止，绝不盲点屏幕中心
val targetPoint: PointF? = order.targetCoord?.let { (wx, wy) ->
    MapCoordinateSystem.worldToScreen(wx, wy)
}
if (targetPoint == null) {
    Log.w(TAG, "军令未含有效世界坐标，无法定位，已中止（不再盲点屏幕中心）")
    callback?.onOrderRejected(order, "军令未含有效世界坐标，无法定位")
    return false
}
```

**前置**：确保 `MapCoordinateSystem` 已 `attach` + 已标定（否则 `worldToScreen` 返回 null，正好触发如实中止）。

**验证**：`MapCoordinateSystem.selfTest()` 通过；传入含坐标的军令，日志应显示换算出的真实屏幕坐标而非屏幕中心。

### 步骤 4：加旋转/尺寸变化监听

**背景**：`CoordinateTransformer.refreshMetrics()` 已能重算缩放，但全仓库零调用点（除了启动/建捕获）。
转屏后坐标映射永久失配，无自愈路径。

**改法**：在 `ScreenCaptureService`（或 `MainActivity`）实现 `ComponentCallbacks`：

```kotlin
override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
    CoordinateTransformer.refreshMetrics()
    // 重算捕获面尺寸 + 记录一行自检日志
    CoordinateTransformer.logSelfTest()
}
```

**验证**：转屏后 logcat 出现「坐标自检通过」，且 scaleX/scaleY 与转屏后的宽高一致。

### 步骤 7：场景图构建器（最高杠杆，0KB 代码）

**新增文件**：`client/app/src/main/java/com/stzb/assistant/ai/scene/SceneGraph.kt`（新目录 `scene/`）

**内容**：
```kotlin
data class SceneGraph(
    val scene: Scene,              // 出征面板 / 大地图 / 城内 / 战报页 / 未知
    val buttons: Map<UiRole, Rect>,
    val troops: List<Troop>,
    val tiles: List<Tile>,
    val marchLines: List<MarchLine>,
    val unknownObjects: List<Rect>
)
```

**核心逻辑**：每帧从 `YoloDetector` 检测框 + `OcrManager` 文本重建。这是「理解战局」的关键中间层：
1. 点击前校验 `buttons[CONFIRM]` 是否存在，不存在就不点；
2. 从检测结果识别「当前在哪个界面」（出征面板/大地图/战报页），而非靠字符串硬匹配；
3. `unknownObjects` 非空时触发「未知界面」处理，而非静默失败。

**验证**：接入现有 4 个 Flow（RoadPaving/ImmunityBreak/SiegeSync/RaidDefense）后，点击动作多了「前置校验」，日志能区分「没找到确定键」和「点到了但界面没跳」。

## 阶段 C —— 训练（2 步，需要你截图）

### 步骤 10：YOLO v8s 11 类训练（最大能力缺口）

**需要你提供**：率土截图，每类 ≥200 张、总 ≥1500 张（覆盖不同分辨率/昼夜/季节/界面状态）。

**流程**（详见 `tools/train_yolo/README.md`）：
1. 采集截图 → 标注（LabelImg/Roboflow，YOLO txt 格式，类别 id 必须与 `data.yaml` 完全一致）；
2. `python tools/train_yolo/train.py --weights yolov8s.pt --epochs 200 --imgsz 640`；
3. `yolo export format=ncnn` → `yolov8n_stzb.{param,bin}` 入 `assets/models/`。

**为什么 v8s 而非 v8n**：11 类里 9 个是小目标（20×20 红点/红线），nano 小目标短板会漏检按钮。

**验证**：`ModelAssetManager` 的 YOLO 能力显示「真推理」；logcat 出现「YOLO 主通道就绪」。
