# 率土全能管家 · 最终方案（能力强化版 · 定稿）

> 制定时间：2026-10-03
> 硬约束：APK < 200MB，端侧纯离线
> 目标：非常实用、能力强、真正有帮助
> 本文件是最终执行蓝图，替代此前所有方案的「能力目标」部分，直接照着开发。

---

# 一、先给结论（回答你反复纠结的那个问题）

**「100 多 MB = 能力弱」是个误区。** 在「率土辅助」这个窄域任务上，124MB 的专用模型组合，
**比 7GB 的通用大模型强一个数量级**，因为：

- 通用大模型（Qwen3-VL-2B 等）首 token 要 3.2 秒，逐帧跑游戏画面物理不可行；
- 专用小模型（YOLO 55ms + OCR 25ms + bge <20ms）能 28fps 连续跑，不发热、不封号；
- 大模型没训练过率土，「出征按钮」这种专属概念它根本不认识。

**真正决定「能力强不强」的不是模型体积，是三件事（都不占体积）：**

| 关键 | 现状 | 做到后 |
|---|---|---|
| 场景理解 | OCR 读出字就硬匹配，中间无理解 | 看懂「这是出征面板/战报页」，给上下文判断 |
| 知识库深度 | 8 条手写战法 + 21KB 假索引 + 写死战损 | 全量武将/战法/守军数据，语义检索准确答案 |
| 数据真实 | YOLO 一张率土截图都没喂过 | 1500 张标注截图，检出真实准确 |

**「真正有帮助」的正确定位：帮玩家做决策，而不是帮玩家自动点击。**
后者封号风险高、游戏一更新就失效；前者玩家离不开、封号风险低、游戏更新也不怕。
你的技术栈（OCR + 场景图 + bge 知识库）天生为「决策辅助」准备，这是最值钱的方向。

# 二、目标形态（这个应用最终长什么样）

一个「率土军师」，核心四个能力，按价值排序：

1. **战报会诊**：截屏战报 → 读文字 → 识别胜负 → 检索战法克制 → 给出「你输在哪、下次怎么打」。
2. **配将建议**：输入/识别武将 → 检索最优战法搭配 → 指出战法冲突。
3. **守军判断**：看地块 → 识别等级 → 检索守军天梯 → 建议「能打/不能打」。
4. **军令解析**：解析同盟军令 → 结构化 → 提醒执行（这是「辅助」而非「全自动」）。

# 三、最终技术选型（已核实为最新最优）

| 能力 | 选型 | 体积 | 依据（2026-10 实测/调研） |
|---|---|---|---|
| 文字识别 | PP-OCRv4 det/rec/cls | 13MB | 基座已下载；率土生僻字比 v3 强 |
| 目标检测 | YOLOv8s（需训 11 类） | 14MB | 11 类里 9 个是小目标，nano 会漏检 |
| 语义检索 | bge-small-zh-v1.5 | 30MB | 端侧中文首选，24M 参数/512维，MTEB 58.3；bge-m3 更强但要 2.2GB 超限 |
| 意图理解 | hfl/rbt3 → INT8 | 20MB | 3 层中文 RoBERTa，军令意图+槽位 |
| 状态建模 | 纯 Kotlin 场景图 | 0KB | 最高杠杆，让「理解」从无到有 |
| 运行时 | OpenCV(arm64) + ncnn + ORT | 39MB | 裁剪后 |

**合计 124MB，余量 76MB。** 基座（`.models/` 278MB）是训练用，不进包。

# 四、详细开发步骤（照着做，共 4 阶段 13 步）

## 阶段 A · 止血（第 1~2 天，不需要任何数据）

### 步骤 1：ABI 裁剪（★最先做，省 165MB）
`client/app/build.gradle` 的 `packagingOptions` 加：
```groovy
jniLibs {
    useLegacyPackaging = true
    excludes += ["**/x86/**", "**/x86_64/**", "**/armeabi/**", "**/armeabi-v7a/**"]
}
```
**验证**：构建后 `unzip -l app-release.apk | grep -c "x86"` = 0。

### 步骤 2：收敛 OpenCV 双来源
先 `grep -rn "org.opencv" client/app/src/main/java/`：
- 无输出 → Java 层没用 OpenCV，删 `build.gradle` 的 `com.quickbirdstudios:opencv:4.5.3.0`；
- 有输出 → 保留 AAR，只做步骤 1。

### 步骤 3：修世界坐标丢弃
`DualTrackSafetyGate.dispatchToPipeline()` 的 `targetPoint`（现在是屏幕中心）改为：
```kotlin
val targetPoint = order.targetCoord?.let { (wx, wy) -> MapCoordinateSystem.worldToScreen(wx, wy) }
if (targetPoint == null) { callback?.onOrderRejected(order, "无有效世界坐标"); return false }
```

### 步骤 4：加旋转监听
`ScreenCaptureService` 实现 `ComponentCallbacks`，转屏时 `CoordinateTransformer.refreshMetrics()`。

### 步骤 5：体积门禁 200MB
`check_assets.py` 的 `DEFAULT_CAP_MB` 185→200；`verify.yml` 传 `--cap-mb 200`；
`build_apk.yml` 构建后加 APK 体积检查（>200MB 直接 fail）。

### 步骤 6：改白皮书假数据
`白皮书.md` 三处（14/130/152-153 行）「185MB/194477273字节/162MB」改为实测。

---

## 阶段 B · 场景图 + 知识库（第 3~7 天，核心价值，不需截图）

### 步骤 7：场景图构建器（★「真正有帮助」的地基）
新增 `client/app/src/main/java/com/stzb/assistant/ai/scene/SceneGraph.kt`：
```kotlin
data class SceneGraph(
    val scene: Scene,              // 出征面板/大地图/城内/战报页/未知
    val buttons: Map<UiRole, Rect>,
    val troops: List<Troop>,       // 兵力、状态
    val tiles: List<Tile>,         // 等级、类型、归属
    val marchLines: List<MarchLine>,
    val unknownObjects: List<Rect>
)
```
每帧从 YOLO 检测框 + OCR 文本重建。**这是从「工具」到「军师」的分水岭。**
- 点击前校验 `buttons[CONFIRM]` 是否存在；
- 判断「当前在哪个界面」；
- `unknownObjects` 非空 → 触发未知界面处理，不静默失败。

### 步骤 8：重建知识库（★「真正有帮助」的内容来源）
抓公开 wiki 语料（全量武将/战法/守军天梯）→ bge 算向量 → 建 HNSW 索引：
```bash
python tools/p1/build_rag_index.py --corpus corpus.jsonl --mode bge \
    --bge .models/bge --vocab .models/bge/vocab.txt \
    --out client/app/src/main/assets/models/slg_knowledge_vector_hnsw.bin
```
**验证**：`check_assets.py` 显示 version=2、dim=512、条目数从 31 → 数千。

### 步骤 9：替换战损假常量
`EdgeSlmEngine.kt:180-181` 的 `myTroopLoss=2300`/`enemyTroopLoss=6800` → 从场景图 `troops` 兵力实测。

### 步骤 10：OCR v4 转换入包
`tools/p1/onnx2ncnn.py` 转 det/rec/cls → `assets/ch_PP-OCRv4_*_infer.{param,bin}` + 字典。

## 阶段 C · 视觉训练（需你截图，1~2 周）

### 步骤 11：YOLO v8s 11 类训练（★「看」的能力）
- 采集：每类 ≥200 张、总 ≥1500 张（不同分辨率/昼夜/季节/界面）；
- `python tools/train_yolo/train.py --weights yolov8s.pt --epochs 200 --imgsz 640`；
- `yolo export format=ncnn` → `assets/models/yolov8n_stzb.{param,bin}`。
**为什么 v8s 不是 v8n**：11 类里 9 个是小目标（20×20 红点/红线）。

### 步骤 12：意图模型（可选，正则可先兜底）
军令合成数据 → `tools/p1/gen_intent_slot_data.py` 生成 → rbt3 微调 → INT8。
短期用正则兜底，不阻塞上线。

### 步骤 13：战报会诊闭环
把场景图 + OCR + bge 串成完整闭环：截屏 → 识别 → 检索 → 生成建议。

# 六、为什么这是「最新最优」而不是「更大」

| 你可能想要的 | 为什么不行 / 不必 |
|---|---|
| 端侧大模型（Qwen3-VL 等） | 最小 600MB，200MB 内物理不可行；且 3.2 秒首 token 跑不了游戏 |
| bge-m3（更强向量） | 召回更高但要 2.2GB，超限；bge-small 已够战法检索用 |
| YOLO26（最新检测） | CPU 更快、小目标更优，但 native 解码器写死 v8 布局，切换要重写 |
| 云端 API | 违反端侧离线前提，游戏时延不可接受 |

**结论：专用小模型分工 + 场景图 + 全量知识库，是 200MB 约束下能力最强的唯一解。**
