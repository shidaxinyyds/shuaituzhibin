### 1. 编译错误 ×4（工程此前**根本无法构建 APK**）

| # | 位置 | 病因 | 修法 |
|---|------|------|------|
| 1 | `TacticalPipeline.kt:249` | `ClickOutcome` 没有 `ok` 成员，却被当 `ClickAndExpect` 用 | `EngineBridge.ClickOutcome` **补上 `val ok: Boolean get() = clicked`**，三处调用点一并成立 |

| 3 | `AccurateFarmingFlow.kt:246` | 同上 | 同上 |
| 4 | `OverlayWindowManager.kt:530 / 882 / 943` | **`scope` 被使用但从未声明**（`Unresolved reference: scope`） | 补 `private val scope = CoroutineScope(Dispatchers.Main + SupervisorJob())`，并在 `destroy()` 里 `scope.cancel()` |

> 第 4 处是原有缺陷，藏在一个 2400 行文件里，仅靠 `grep "coroutineScope"` 找不到。

**枚举常量**（`ButtonType.X` / `TaskType.X`）与**整对象成员**（`EngineBridge.x`），
`局部变量.属性` 与 `this 成员` 都不在它的射程内。详见 §五 的自建校验器。

## 二、P1 联动与逻辑坑（已修）

### 1. 「防掉线微保活」此前永远不触发

`TacticalPipeline` 新增统一判据：

```kotlin
val isRaidPatrolActive: Boolean
    get() = activeTaskType == TaskType.RAID_DEFENSE || activeTaskType == TaskType.NIGHT_SENTINEL
```

- `AutoPilot.ensureRaidPatrol()` 与悬浮窗 `patrolRunning` 全部改用它。
- 修掉的行为：此前判 `== RAID_DEFENSE`（activeTaskType 恒为 `NIGHT_SENTINEL`）→
  敌袭态下每 60 秒把正在运行的哨兵拆掉重建 → `startPatrol()` 里
  `lastKeepAliveTimeMs` 每 60 秒归零一次，而保活周期是 5 分钟 → **5 分钟微保活永不执行**。
- 顺带修掉：军师面板谎报"雷达哨兵未巡查"。

### 2. `stopCurrentTask()` 类型映射错位

`TACTICAL_SCHEDULE` 原先被并进 `IMMUNITY_BREAK` 分支 → "停定时任务却去停了破免流"。
已拆开：定时任务的任务体是本类内的 `executeTimedDispatch`，取消 Job 即可收尾。

### 3. 邮件法令解析两处坑（痛点 2 的输入源）

| 问题 | 修法 |
|------|------|
| 注释说"含『要塞/集合』才取第 2 个坐标当要塞坐标"，**代码无条件取 `coords[1]`** → 可能把部队提前调往随机地点 | 按注释实现：新增 `mentionsFortress` 判定（要塞/集合/集结/前线） |
| 未识别到时间时**静默默认 21:00:00**，调用方无法分辨"读到"与"猜的" | `SiegeMailPlan` 新增 `timeFound: Boolean`；缺时间时置信度由 0.85 降到 0.70；`startSiegeFromMail()` 显式 WARN 提示基准是猜的 |

## 四、五项"摆设"补实

### 1. 税收熔断（痛点 4 核心）—— 已实现

`DailyLogisticsFlow.performTaxLevy()` 现在是**三重保护**：

1. **自然日次数上限**：`maxDailyTaxTimes`（默认 3），跨天自动清零，持久化在
   `stzb_logistics_state`（`tax_date` / `tax_count` / `tax_last_at`）
2. **同日内冷却**：默认 60s
3. **付费熔断**：点击前与确认弹窗出现前各扫一次屏，命中
   `玉符 / 元宝 / 充值 / 购买 / 花费 / 消耗玉` 等关键词即**放弃本轮**

   为什么必须做：`ButtonType.TAX` 的别名表里**同时含"征税"与"强征"**，
   纯靠按键文字无法区分免费/付费，只看上下文代价提示才能避免误扣玉符。
4. 只有真正走完点击流程才 +1 记账；并新增 `todayTaxCount()` 供 UI/日志查询真实进度。

### 2. 体力防溢：从"只喊不做"改为**真正派发消耗**

`consumeOverflowStamina(slot)`：
- ≥110 告警、≥120 满溢，两级均派发
- 在出征选队面板内定位 `ButtonType.TRAIN`（练兵）→ 点击 → 确认
- **找不到就如实报告"本界面无练兵入口，已记录待处理"**，绝不盲点坐标
  （宁可少消耗一次体力，也不能猜错按钮把部队派出去）
- 新增 `enableStaminaConsumption` 开关（默认 true）

### 3. 屯田「优先 Lv.5+ 资源地」—— 已实现为**拒绝**而非"继续执行"

原先低于门槛只打印"收益偏低（继续执行）"，等于把 3 策令 + 20 体力花在低收益地上。
现在默认 **拒绝本次屯田**并说明原因（与 `validate_logistics_farming.py` M4
"level < min_level → 过滤掉"语义一致），可用 `allowBelowMinLevel = true` 显式放开。

### 4. 打铁领取：不再"无条件报成功"

原实现是"看到 CONFIRM 就点 → 无条件打印『收益入库』"——手势失败也算成功。
现在按**点击与确认的真实返回值**给结论（成功/失败/无可领取三分支），
把失败如实报告，避免玩家以为材料已到账。

### 5. `DualTrackSafetyGate` 从死代码 → 真正可用的军令闸门

修掉它被摘出调用链的那个缺陷（丢弃世界坐标、改用屏幕正中）：

- **不再改写目标**：订单的世界坐标原样向下传（各流都支持 `worldCoord`，
  由流自己用 `MapNavigator` 对准镜头），屏幕坐标仅作"已对准镜头中心"的占位
- **宁可拒绝，也不猜**：
  - 需要坐标的意图 + 未标定 → **拒绝**并提示去「标定」页签
  - 需要坐标的意图 + 无坐标 → **拒绝**（不允许用屏幕正中顶替）
- `verifyAndDispatch` 改为 `suspend`，新增 `parseAndDispatch(decreeText)`
- **接线**：悬浮窗军师页签新增 **「⚔️ 执行该军令（经安全门禁）」** 按钮，
  把 `lastExtractedOrder` 真正送进流水线（此前 `lastExtractedOrder` 只用于拼状态文案，
  **解析出来却永远不会打出去**），并通过 `SafetyGateCallback` 把结论写进日志流

## 五、端侧 RAG：PVE / PVP 分流（已实现）

`SlgRagEngine` 新增：

- `enum class ReportType { PVE, PVP, UNKNOWN }` + `detectReportType(text)`
  （PVP 优先：会战战报里也常出现"守军"字样，容易误判成 PVE）
- `BattleDiagnosisResult` 扩展 `reportType` / `pveAnalysis` / `pvpAnalysis`
- **PVE 路径** `analyzePveDefense()`：
  - 守军**暴走 / 反击 / 狂怒 / 免疫**机制识别（命中即给出对应处置建议）
  - **补刀阈值**：按地块等级的建议兵力 × 残余系数（`PVE_KILL_THRESHOLD_RATIO = 0.35`，
    可按赛季调整）折算并向 500 取整；**明确标注是经验估算、非精确读数**，
    避免被当成精确值做高风险决策
- **PVP 路径** `analyzePvpSpeed()`：
  - **先手判定**：优先读战报原文的"速度 xxx"数值；读不到则用武将基础速度参考表
    （明确标注"不含装备/加点/阵营加成，需以属性面板实测为准"）
  - **同类指挥战法增伤冲突**：`神兵天降 / 大赏三军 / 避其锋芒 / 始计 / 绝水遏敌`
    同时出现 ≥2 个即判为"互相覆盖、浪费战法位"
  - **加点超车建议**：落后则给差值目标，持平则建议单点领先 5~10 点
- 微脑层 `EdgeSlmEngine.diagnoseBattleReport()` 接入分流结论，
  并**移除写死的假战损**（原 `myTroopLoss = 2300 / enemyTroopLoss = 6800` 与战报毫无关系），
  改为从原文解析，读不到就如实报 0

### 新增的两道 CI 闸门（补上 `verify_refs` 的射程盲区）

`verify_refs.py` 的成员对账只覆盖**枚举常量**与**整对象成员**，因此查不到
`局部变量.属性`、`this 成员` 与**具名实参**。本次 4 处编译错误全部落在它的盲区里，
于是"工程编不出 APK"在当时的闸门下一路绿灯。为此新增两个必需检查：

| 新检查 | 拦什么 | 自测（注入缺陷） |
|--------|--------|------------------|
| `tools/check_undeclared_receivers.py` | `scope.launch` 而 `scope` 从未声明 → `Unresolved reference` | 反例报 1 处 / 正例 0 处 ✅ |
| `tools/check_ctor_named_args.py` | `Foo(a = 1, c = 2)` 而 `c` 不存在 → `No parameter with name` | 反例报 1 处 / 正例 0 处 ✅ |

两者的**零误报**是刻意做的硬要求（项目里已有共识："一个会误报的检查比没有检查更糟，
因为它会训练人忽略它"）。为此处理了这些坑：
- 具名参数检查必须**先剥离注释**：本项目构造参数上普遍带中文注释，注释里的逗号
  会把参数名切碎——第一版因此报出 30+ 条全部是假的；还必须按**嵌套深度**切分
  （`Map<String, Int>`、`listOf(1, 2)` 里的逗号不是分隔符）。
- 接收者检查必须纳入：包名根段（`com`/`java`/`kotlinx`/…）、解构声明与解构 lambda、
  `::class.java`、`entries`/`resources` 等。**第一版漏了 `kotlinx`**，导致正例被误报。

### 顺带修掉的工具链缺陷（上一轮审计发现）

`check_ci_shell.py` 在**模块顶层**做 `except ImportError: sys.exit(2)`，
而 `SystemExit` 继承自 `BaseException`、不属于 `Exception`——
`run_all_checks.py` 的 `except Exception` 拦不住它，于是缺 PyYAML 时整条回归
**在第 5 项被掐断**，看起来像"后面都过了"（假绿）。双管齐下修复：

1. `run_all_checks.py`：加载校验器时改捕 `BaseException`，让单项失败不再掐断全局；
2. `check_ci_shell.py`：把缺依赖判断从模块顶层推迟到 `main()`，只影响本项。

实测：用**没有 PyYAML** 的解释器运行，现在能跑完 21 项（`ci-shell` 单独 FAIL 并说明原因），
而不是跑到一半消失。

## 七、遗留事项（**未做，且必须知悉**）

   都需要设备（仓库内至今没有任何 APK 产物）。

   `Install dependencies` 步骤已包含 `pip install pyyaml`，因此新增的两道闸门
   在 CI 里不会因缺依赖而失败（本地若用不自带 PyYAML 的解释器，`ci-shell` 会单独 FAIL 并说明原因，
   不会再掐断整条回归）。
