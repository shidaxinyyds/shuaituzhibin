# 09 · 视觉架构终版分工（定稿）

> 本文固化本项目视觉感知的**最终技术分工**，终结"YOLO 到底该不该用、用在哪"的反复摇摆。
> 后续任何视觉能力的增改，先对齐本表的"判据 + 归属"，再动手。

## 0. 设计公理（不可违背）
- **Fail-Closed**：识别无足够把握即 `UNKNOWN`，绝不据此自动出征/避让等高危决策。
- **零伪造产物**：没有真权重/真模型就如实缺席，不空改名、不造死代码（对齐"严禁死代码"）。
- **确定性优先**：固定 UI 目标一律走确定性；学习模型只兜"确定性原理上做不到"的那部分。
- **体积 ≤185MB**：现入包 73MB；学习通道预留 ~10–15MB。

## 1. 分工总判据（唯一一条轴）
判断一个视觉目标归确定性还是学习检测，只看一件事：

> **屏幕上的目标，是不是"干净、孤立、已知位置、由固定 sprite / 纯颜色 / 文字定义"的？**

| 是 → 确定性（模板匹配 / HSV 分割 / 网格几何 / OCR） | 否 → 学习检测器（YOLO 系） |
|---|---|
| 固定按钮、固定立绘、单目标、已知槽位 | **密集**多实例、**多类别**同时找 |
| 由颜色定义（红地、金罩、红线）、由文字定义（按钮文案） | **跨多种缩放**、**互相遮挡**、**任意构图** |
| 例：UI 面板、守军头像、邮件红点 | 例：整张大地图上的部队/地块/建筑/行军 |

**关键澄清**：游戏美术资产是"有限固定 sprite 集"，但**屏幕上渲染的是这些 sprite 在等距投影下的任意组合**（十几种缩放、被地形/彼此遮挡、被阵营色染色）。"资产固定"不等于"画面固定"——遮挡 + 跨缩放 + 密集堆叠一叠加，模板/颜色/几何就崩，这正是学习检测器的领域。

## 2. 分层归属表（每类目标 → 引擎）

| 视觉目标 | 归属引擎 | 方法 | 状态 |
|---|---|---|---|
| 出征/驻守/撤退/确定/取消 等按钮 | `StzbUiMatcher` | OCR 语义 + 多尺度模板 + 随用随学自登记 | ✅ 已有 |
| CANCEL 取消键 | `StzbUiMatcher` | 枚举 + 知识库别名，经既有择优/触控通用可用 | ✅ 本轮新增 |
| 行军红线 / 敌袭告警 | `RaidRadarDetector` | HSV 双区间红掩膜 + HoughLinesP 向量 + 源头回溯 + 边缘红闪 + OCR 倒计时 | ✅ 已有（YOLO 反而给不出向量/源头） |
| 资源地 / 要塞 / 免战罩 | `TileStatusDetector` | 金色 HSV + 轮廓几何 + OCR 读等级/资源/倒计时 | ✅ 已有 |

| **大地图 troops/tiles/buildings/march** | **学习检测器（YOLO 重锚）**（见 §4） | 密集多类、跨缩放遮挡的地图目标检测 | 💤 休眠，待功能立项 |

## 3. 守军武将 → 确定性头像图库（定论）
**结论：武将身份识别不上 YOLO，走确定性图库。** 依据：NPC 守军均为标准立绘、不带皮肤；面板头像槽位固定。

### 3.1 双模式兼容（默认走 B，A 为加速）
- **模式 A｜整队组合指纹**：每个土地等级的守军是"那几套固定组合"，可缓存整屏守军面板的感知哈希/关键槽拼合指纹，命中即秒得"是哪一队"。
- **模式 B｜单人头像模板库**（**准绳，A 扛不住时的兜底**）：`assets/defender_refs/<武将名>.png` 一人一张；运行时裁固定槽 → `OpenCvMatcher.match` 逐个比库 → 得守将身份集合。
- 保险起见 B 为准：组合再多，武将池有限，几十张头像即全覆盖；A 仅在"确属固定组合"时提供加速捷径。

### 3.2 数据来源：离线榨标签，非运行时收集
- 由用户**一次性提供各等级守军面板截图**；离线工具从**固定头像槽**自动裁出每人头像，标签取自**同屏能 OCR 读到的武将名**（离线、一次性）。
- **不做运行时自动采集钩子**——固定模板场景下它既无必要、又依赖未验证的空间假设、还可能静默攒废料。

### 3.3 运行时链路与安全
- `DefenderTemplateClassifier`：裁当前面板固定槽 → 匹配头像库 → 守将身份 → 喂既有 `DefenderEvaluator` 出危险度。
- **同时收紧现有守将名提取**：现 `EngineBridge.evaluateDefenders` 把**所有 OCR 文本**当名字，未命中者被 `DefenderEvaluator.findMatch` 兜底成 `MODERATE`（虚增/假确定）。改为**只认命中武将名库的才算守军**，其余丢弃；一个都不认且非头像兜底 → `UNKNOWN`（延续 fail-closed）。
- 头像**只携带"是哪个武将"**，不含等级/兵力 → 是 OCR 名字的**兜底与交叉校验**，不替代 OCR。

## 4. YOLO 重锚：大地图目标检测（对齐 02_最优解 的 Scene）
**结论：YOLO 不删，但从"全 11 类主检测器（含按钮/红线）"重锚为"大地图多目标检测器"。**

### 4.1 目标类表（替换旧按钮/红线 taxonomy）
对齐 [docs/02_最优解方案与缺陷对照.md](./02_最优解方案与缺陷对照.md) 的 Scene 规格：
- `troops`：我方/敌方/同盟/中立 部队标记（含行军中的小 sprite）
- `tiles`：地块（等级、类型、归属）
- `buildings`：要塞/关隘/码头/军阵/箭塔/拒马/营帐/据点
- `march_markers`：行军部队（兵种、大致兵力规模、是否带名将）

### 4.2 价值（解锁下一代能力，非改进现有流程）
- **自动选靶 / 清野 / 集火**：一屏同时框出可欺负目标并分类。
- **敌袭预警升级**：读"来的是多少兵、什么兵种、带不带名将"，比红线的"有情况"更硬。
- **建筑/设施跨缩放识别**：任意缩放 + 遮挡下仍泛化。

### 4.3 数据与成本（诚实）
- 遮挡/密集正是弱监督榨不出标签处：需**中等标注集**（几百~低几千张地图截图）。策略：确定性先标**易例**，人工只点验**难例**。
- 形态取 `yolo26n` INT8（~10MB），预留于 185MB 预算内；赛季换皮需周期性再训。
- **仅作候选/建议**，低置信绝不触发自动出征。

### 4.4 触发条件与现状
- **现状**：自检项标 `☑ 未启用（可选增强通道）`，不计不合格；`YoloDetector` 作 ncnn 休眠通道保留，未删（对齐"零伪造/不删待用"）。
- **开工触发**：仅当产品决定建"自动选靶 / 大地图态势感知"那天，才把 `data.yaml` 重锚到 §4.1 类表、标注、训练、接入 Scene。
- 在此之前，`hero_face_detector` 等改名一律**不做**——名实不符即违背零伪造。

## 5. 头像图库 vs YOLO 的边界（一句话）
> 图库管"**单个固定立绘是谁**"（守军面板，干净孤立）；YOLO 管"**满屏乱七八糟里有几队、谁、在哪**"（大地图，密集遮挡跨缩放）。二者不重叠、不互替。
